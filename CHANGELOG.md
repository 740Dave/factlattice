# Changelog

## Unreleased

### Fixed (`tools/vocab_edit.py add-lookbehind` accepts a row that starts with `(?i)`)
- A row whose pattern starts with exactly `(?i)` was refused, because `(?<!T)(?:(?i)x)` is invalid in Python. The guard compiles every rules-file rule case-insensitively already (`Rule` in `tools/disclosure_guard.py` defaults to `flags=re.IGNORECASE`), so the leading `(?i)` is redundant: `add-lookbehind` now rewrites the row as `(?<!T)(?:<rest>)` and runs the same post-rewrite checks. Any other global flag group (`(?s)`, `(?x)`, `(?im)`, `(?a)`, or a second group after `(?i)`) is still refused. The printed output is unchanged in kind (counts, line numbers, names). Tests: `tests/test_vocab_edit.py` (a fuzz of 6,000 strings, for the five planted patterns, shows the old and new patterns match the same spans when T is absent).

### Added (`tools/vocab_edit.py`: edit the disclosure guard's private rules files blind)
- A stdlib-only tool for refreshing `private/publish-vocabulary.tsv` or `private/disclosure-denylist.tsv` without the maintaining agent reading them: `append`, `add-lookbehind` (rewrite every row whose pattern matches a probe to `(?<!T)(?:<old>)`), `remove` and `count`. It reads and writes the file itself and prints counts, line numbers and the text of a row's fourth column when that text is slug-shaped (letters, digits and single hyphens, either case), no loaded rule or builtin matches it and the guard loads the row; anything else there is withheld. A stray tab in any field (pattern, control or reason) shifts row text into the fourth column, so keep tabs out of every field; the tool refuses tabs in what it writes itself. (An internal error prints its class name only.)
- Every write op refuses text with a tab or a line break, changes only the bytes of the rows it names, writes atomically, then loads the file back with the guard's own parser and runs the guard's controls. If any check fails it restores the original bytes and compares them with the original (exit 1); if the restore itself fails it says `ORIGINAL NOT RESTORED`, prints the backup's path and exits 3. The backup (a full copy of the private file under `$TMPDIR`) is deleted once the check has passed or the restore is verified, and kept only when the original was not restored; a write refuses to run when `$TMPDIR` is unset or not writable (a dry run needs none). `--dry-run` runs the same checks and writes nothing.
- `add-lookbehind` checks that the rewrite worked (the text placed directly before the row's own match in the probe must no longer match from inside that match) and refuses the whole operation, writing nothing, when a row still matches or starts with a global inline flag. Names are printed: `append` refuses a name that a loaded rule matches, and an existing name is printed only when it is slug-shaped (`^[a-z0-9]+(?:-[a-z0-9]+)*$`, ASCII, either case) no loaded rule or builtin matches it, and the guard loads the row; any other name is shown as `(name withheld, line N)`, whatever the row's column count. The default `--file` honours `FACTLATTICE_PUBLISH_VOCAB` as the guard does.
- `tests/test_vocab_edit.py` runs on planted files and asserts that neither stream carries a planted pattern, control or reason, or text the caller typed, for the refusal paths, the compile-error path, the bad-usage paths (an invalid subcommand, an extra positional), the internal-error handler and the crash-after-write path, each shown to fail against a mutant of the tool. Not asserted by a test: the traceback of a KeyboardInterrupt, and Python's own warnings (a regex FutureWarning prints a code line and a position, not rule text; checked by hand).

### Fixed (the disclosure guard no longer reports a short id found inside a shipped product name)
- `tools/disclosure_guard.py`: in tree and publication mode, a rule the guard generated from a plain agent id (ASCII letters, digits, single hyphens; name `neutrality-agent-id`) is applied with each occurrence of an exempt shipped agent name overwritten by filler of the same length, so a shorter generated id that is part of a shipped name is not reported inside it, in the file or its path. It is reported anywhere else, including elsewhere on the same line. An occurrence is the exact name in its own case with no word character (any script), `-` or combining mark on either side. Every other rule is applied to the text as it is, whatever its name: a row of a rules file (even one named `neutrality-agent-id`), `neutrality-corpus-id`, and a generated agent id with any other character in it. The staged check, the PR leak check and release notes do not apply it. Known limit: it has no off switch. Tests: `tests/test_neutrality_terms.py` (`test_f2_*`); the selftest's tree-mode control (run by `--selftest` and `--publication`, not by `--tree`) goes red when the exemption is inert or mute, and when it masks any of five planted rules inside a made-up exempt name: a rules-file row, a row named `neutrality-agent-id`, a hand-built non-generated rule of that name, a generated agent id with a `.`, and a generated corpus id with a plain id (the rows and generated ids are built by the real row loader and rule generator). What counts as an occurrence of a name (case, boundaries, combining marks) is pinned by the `test_f2_` tests, not by the control. The private contexts table is the maintainers' input: a context fragment changes what an id rule matches, and the exemption trusts it.
- `SPEC.md` (the example `generator` string) and `SDLC.md` (the kill-switch commands) no longer name the internal repository or the old parser's name.

### Changed (the build stamp covers the core package; its values change once)
- `build_stamp` (the value the code-currency sentinel watches to re-exec a running server) now hashes the `.py` source of both `factlattice_engine/` and the core `factlattice/` package, each file named in the hash by a package-prefixed path. Before, a change that touched only `factlattice/` (the parser, the authoring writers) never moved it, so no server relaunched. The core package is found through the import the server itself uses, never a fixed path.
- Every stamp value changes once, because the hashed paths now carry a prefix: `build.source_sha256`, `engine_sha256` and `core_sha256` in the `call_context` of `python -m factlattice_engine call`, the miss-log's `engine_build_stamp`, and the node-change ledger's `engine_head`. `source_sha256` is now the stamp itself (it was a hash of the two package hashes). Compare stamps only between records written by the same version.
- A stamp that cannot be read (an unreadable file or directory, a core package that cannot be found) is still fail-safe (no re-exec), but is no longer silent: the sentinel logs it once per change of state, naming the error class and never a path. A sentinel that started with an unreadable tree adopts its first later readable stamp as its baseline and logs that. Editor lock files (`.#name.py`) and dangling symlinks are skipped, since neither is source.
- Only `.py` files are stamped: a change to package data (for example the selfcheck control corpus) does not move the stamp.
- The roots the stamp walks are the packages in `build_stamp.STAMP_PACKAGES`, each located as the process imports it, so adding a package to that tuple (as SDLC [BUILD-STAMP-ROOTS] requires when it joins pyproject's package list) is enough for its changes to re-exec servers.

### Changed (the placeholder-time detector's text says what the single-quote rule does)
- `factlattice/authoring/unread_time_shared.py`: text only, no behaviour change. The limit sentence now says that the plain pairing counts every single quote on the line, so a token whose only quotes are single quotes is always refused when an odd number of apostrophes inside words lies before it on its line, inside the phrase or before it, and otherwise the result depends on every quote on the line; the refusal advice and SPEC 4.6.6 say single quotes "can fail, for example when an apostrophe inside a word (as in it's) comes before the token on its line" in place of "may not when the quoted text contains an apostrophe"; the index line says `quoted_spans` is one half of the exemption. The module's hash pin moves (`tests/test_unread_time_guard.py`, SPEC, SDLC), and the copy in the other repository is to be updated to match after this merges, before the engine goes live.

### Changed (the typed writers make no backup for a file under an ephemeral root)
- `_write` makes no pre-edit copy when the file's realpath is under an ephemeral root, decided by the node-change ledger's own predicate (`ledger.is_ephemeral`: the OS temp dir, `/tmp`, `/private/tmp`, or the roots in `FACTLATTICE_LEDGER_EPHEMERAL_ROOTS`). The write is unchanged. The receipt has `backup_path: null` and `backup: {status: skipped, reason: backup-skipped-ephemeral}` (the key is absent when a backup was made); the text report says `no backup: the file is under an ephemeral root`. `FACTLATTICE_BACKUP_EPHEMERAL=keep` makes backups of such files anyway (the ledger still skips them). Other files are as before, including `FACTLATTICE_BACKUP_DIR` and `FACTLATTICE_BACKUP_KEEP`. Before this, test suites run in temporary directories filled the backup folder with copies of files that were deleted with their directories (a backup folder of 94.6 GB, measured), which the per-file retention cap does not bound.

### Changed (the typed writers prune their own backups)
- After a successful typed write, `_write` deletes all but the newest N backups of the file it wrote, in the backup directory (`FACTLATTICE_BACKUP_DIR`, or `factlattice-backups` under the temp dir). N comes from `FACTLATTICE_BACKUP_KEEP`: an integer of 1 or more; unset, empty or an integer that is 0 (`0`, `00`) means the default of 20; `all` keeps every backup (the old behaviour); any other value means the default and adds a receipt warning that names the variable and does not echo the value. A backup is matched to its file by the file name and the path digest in the backup's name, so another file's backups, including one whose name begins the same, are never touched, and the backup the write just made is never deleted. "Newest" means the newest local-clock stamp in the backup's name: after a clock step back (a DST fall-back, an NTP step) the backups made in the repeated hour can rank below older ones and be pruned first, while the write's own backup always survives. A prune failure is a receipt warning naming the error class, never a write failure. Before this the directory was never pruned (one heavily written file left 4100 full copies in two days).

### Added (a deployment overlay: one optional directory, `FACTLATTICE_OVERLAY`)
- `factlattice/overlay.py` is the one resolver of the deployment overlay. `overlay_root()` returns the directory the variable names when it is an absolute path to a real directory (a link is refused, checked with `lstat` of the normalised path, so `link/` and `link/.` are refused too), None when the variable is unset or empty, and when it is set but unusable it warns once (a dev or CI run) or, with `strict=True` (a required `tools/release_prep.py` run), raises. Only the resolver may read the variable: `tests/_registry_guard.py` has a separate scan for it, with a negative control. The layout and the rules are in `PUBLISHING.md`.
- The engine reads `<overlay>/domain-profiles/*.lts` after the shipped profiles (an explicit `FACTLATTICE_PROFILE_DIR` is still the whole set), and the registry's identity hash covers the names and contents of the profiles it loads (an overlay that loads none changes nothing). With no overlay nothing changes.
- `tools/release_prep.py` prints and records a `deployment overlay:` line, refuses in required mode when the variable is set and unusable, and never passes the overlay to the snapshot's suite.
- The suite removes the overlay variable from every test's environment; a deployment-only test takes the `deployment_overlay` fixture to get the run's own state back.
- `pytest` prints a `deployment overlay:` line in its header: a run with no overlay says that its deployment-only tests skip.

### Added (publication tooling: `word_ids` in the neutrality terms file)
- `tools/disclosure_guard.py` reads an optional `word_ids` list in the generated terms file (each entry stored exactly as in `agent_ids` or `corpus_ids`, case included, plain codepoint order, unique; validated, and covered by the header sha256), and applies two matching rules: a listed word id is matched in upper case or as its stored form between path separators, never as a bare word; an id of three characters or fewer is ALWAYS matched in upper case only and not inside a hyphen-joined upper-case or digit run, whether or not the file has the key. A file without the key is otherwise matched as before. The matcher is pinned to a shared case table copied byte for byte into `tests/data/term_regex_cases.json`. A shipped short or listed word id is now exempt by its id (its rule's control is its upper-case form). The run line says whether `word_ids` was in force and how many ids it narrowed.

### Added (publication tooling: the neutrality terms input of the disclosure guard)
- `tools/disclosure_guard.py` can read one optional generated terms file of agent and corpus ids (`--neutrality-terms FILE` or `FACTLATTICE_NEUTRALITY_TERMS`), made by another tool, and turns each id into a rule named `neutrality-agent-id` or `neutrality-corpus-id` whose control string is the id itself, so `--selftest` proves each one fires. Matching is whole-token (a letter or digit beside the term blocks a match, a hyphen or underscore does not), case-insensitive except an all-capital term of five characters or fewer, and skips a term inside a listed false-positive context; the table of contexts is read from a private file (`--neutrality-contexts`, `FACTLATTICE_NEUTRALITY_CONTEXTS`, or `private/neutrality-term-contexts.json`) and none ships. The file is validated before any use (shape, no unknown top-level key, sorted non-empty lists, sha256 over the canonical JSON of the two lists, `generated_at` strictly `YYYY-MM-DDTHH:MM:SSZ`, under 21,600 s old, not more than 300 s ahead, hand additions present); the first failure names its cause (`missing`, `unparsable`, `shape`, `sha256-mismatch`, `future-dated`, `stale`, `partial`) and never a term, and nothing is loaded from an unusable file. With the file absent, `--selftest`, `--tree` and the staged check print one warning and are otherwise unchanged; `--publication` refuses when a named file is unusable, and refuses when none is named if `--require-neutrality-terms` is given. A generated agent id that exactly equals the stem of an `agents/<stem>.md` regular file (never a link) in the tree being scanned (after PUBLISH-EXCLUDE) is exempt as a shipped product name and is listed by name in the run output. A generated corpus id is exempt only when its corpus ships in the scanned tree (derived from the deployment registry, read through the engine's own loader, and the tree) and the engine would serve it as a non-private corpus; with no usable registry none is exempt, and one line says why. `--expect-neutrality-terms-sha256` makes the guard refuse a file that hashes differently from the one the caller validated. `tests/test_neutrality_terms.py`.

### Added (publication tooling: interim release notes)
- `tools/release_notes.py collect` and `render` produce release notes for a range of a repository's merged pull requests. `collect` writes a schema-1 JSON of the PR merges in `--from..--to` (every parent, once per PR; a commit counts for PR N only if GitHub names it as N's merge commit): the CHANGELOG lines the release adds (present at `--to`, absent at `--from`) each credited to the PR that added it, with the group and the rule that decided it (CHANGELOG heading, then label, then file class); `render` writes Markdown in fixed groups from that JSON alone, each line under its own heading's group and cited `(#N)`, a PR with no CHANGELOG line under "Needs a line" (no words invented, no summary paragraph) and a footer count equation that must balance. `render --public` shows no PR title and no PR number, leaves the internal groups out (counted), applies a config's `public_strip` patterns, and runs the disclosure guard first; it is refused when the guard's private files are missing or it finds anything. PR bodies are never read. A repository is a JSON config (`tools/release_notes/`), so a second repository needs no code change; a public ref is mapped through a `release_prep` snapshot record. It never pushes or opens a pull request. SDLC.md 7.6 `RELEASE-NOTES-WORDS-ONLY-FROM-CHANGELOG`; PUBLISHING.md.

### Added (publication tooling: the public test set; `specs/42-publication-workflow.lts` R10, T10)

### Added (publication tooling)

### Changed (tool arguments)
- Every tool refuses a call that carries an argument name its advertised input schema does not declare: `success: false`, `refused: true`, `code: unknown_argument`, `unknown` (every undeclared name, sorted), `nearest` (each name's closest declared name, or null), and nothing is evaluated. Before this a misspelt filter such as `prefixx` was dropped without a word and the answer widened to every node. Values are never echoed. ### Changed (tool replies: minted keys named; a note for consumers)
- Since spec 39, every node's `properties` carries the minted key `normative_effective` (`true` or `false`), so a consumer that compares a node's authored lines with its read-back `properties` as a whole sees one key more than it wrote. Replies now name it: every node object in a reply that a served tool returns (an object with a string `id` and a `properties` mapping) also carries `minted_keys` beside its `properties`, the sorted list of the keys of that `properties` that the engine minted (today `["normative_effective"]`; empty when none). A library caller that reads parsed nodes directly uses `core_keys.ENGINE_MINTED_KEYS` and `core_keys.minted_keys_in`. The key stays inside `properties` (a `where` condition still filters on it) and `property_count` still counts it. A whole-`properties` comparison should drop the keys `minted_keys` names, and should not keep its own list of them; a renderer that shows a node's properties to a reader should skip the keys `minted_keys` names by default and show them only when asked. Every node object in a served reply now has one more field, `minted_keys`, so a comparison of a whole reply object (not just its `properties`) sees it too. A digest row carries no `properties` and gains nothing. The minted set is defined once, as `core_keys.ENGINE_MINTED_KEYS`, and stated in SPEC.md §1.3.4. The field is added at `tools.dispatch`, so a caller that calls an `LtsEngine` method directly does not get it. The field is not counted by `token_budget`, and the query log's `elapsed_ms` now includes the walk that adds it (measured about 2.7 microseconds per node). The selfcheck control is unchanged.

### Added (disclosure guard: publication mode; `specs/42-publication-workflow.lts` R1, R2, R5, R6, R7, D2)
- `tools/disclosure_guard.py --publication [DIR]` is a mode of its own, the publication gate, and the only mode that fails closed. It exits 1 (the integrity code) when the vocabulary file or the denylist file is missing, is empty (comments and blank lines are not rows), yields no usable rule, or has a row refused at load (malformed, bad regex, or a pattern that misses its own control), and when the selftest controls or the tree-mode control fail. The message names which file and why, by label and line number, and prints no pattern or control. Before this, `--tree` refused only a missing vocabulary file and passed with the denylist file missing or empty (and printed the pattern and the control of a refused row). `--tree` is otherwise unchanged. Publication mode always walks the directory on disk (never `git ls-files`; `.git` left out; a symlink is a shipped file and its target string is scanned; a dangling one is counted), and refuses a directory that does not exist, is not a directory, or yields zero files shipped or scanned, two private files that are the same file or have the same sha256, and an unreadable PUBLISH-EXCLUDE. The tripwire wording is on the RED and REFUSED result lines as well as the green one, and the result line is printed after the report is written (a failed write ends RED or REFUSED and names it). The scanner's exempt files (`tools/disclosure_guard.py`, `tools/pre-commit`) are now matched as exact paths, in every mode, not as prefixes.
- Every `--publication` run, green, red or refused, prints ONE scope line: files scanned, exclude entries applied, files shipped, the scanner's own exempt files by path, each private file's rule count, row count and sha256, the mapped-file count and the builtin rule count; then a result line that calls the scan a lexical tripwire over the named vocabulary and never says nothing private is present. A finding is `path:line  [rule]`: the text of a content line is never printed, and where a path itself matches a rule the matched span of the path is masked with `*` (the exempt paths in the scope line too). Known limits: a zero-width (lookahead) rule leaves nothing to mask, and the rule name is printed by design. `--report FILE` writes the same fields, the findings (path, line, rule) and the exit code as JSON. `--map-manifest FILE` (lines `target<TAB>source`, for files placed by the snapshot builder's folder map) adds the mapped count and names the source beside a finding in a mapped target; a target that is not a file in the tree, is excluded, is listed twice, or a malformed line, refuses.
- The lenient modes (staged, `--all`, `--selftest`, `--tree`) stay lenient, but a run with a private file missing or EMPTY no longer prints a zero-findings result: it says which private file was not loaded and that its rules were not checked ("UNCONFIGURED RUN, NOT A CLEAN RESULT"). Exit codes are unchanged except `--selftest` with an EMPTY private file, which now exits 2 (unconfigured) as it already did for a missing one. `tests/test_disclosure_guard_publication.py` is new; `tests/test_disclosure_guard_tree.py` now gives its fixture a non-empty denylist, because an empty one no longer prints the clean line.

### Changed (bounded root reads, slice 4 of `specs/38-bounded-root-reads.lts`: boot and `build_store`)
- The server answers `initialize` without reading any root. Every corpus starts PENDING and joins the store, in the registry's order, as its read ends. A call naming a pending corpus waits for it up to `LTS_ROOT_DEADLINE_S`, then is served or refused `root-unresponsive` (`root_health.status` `pending`, or `unresponsive` once a root of it went a deadline with no progress). `lts_list_corpora` never waits and lists a pending corpus with null totals; a corpus-omitted read waits once for all of them, then leaves out what is still unread and declares it (`corpora_skipped`, `complete: false`). In the normal boot (about a second and a half) no call sees a refusal it would not have seen before. After a land every corpus is pending again.
- A write to a file under a root that is still pending, or under a corpus still being read, now WAITS for that root's first read and for its corpus to be published (slice 3 refused it at once), then lands or is refused `root-unresponsive`.
- A corpus whose root did not answer at boot stays pending and is read again, with no restart, when the stuck call returns.
- `config.build_store` is bounded for every caller. A corpus whose root does not answer inside the deadline is not served and is in `store.failed_corpora` with the new code `corpus-root-unresponsive` and NO path (`{code, path: null, private}`). The call returns in about one deadline however many roots hang, because every root is read at once on its own worker. A root with a stuck worker, or a process already holding 16 stuck workers, fails its corpus at once with no new thread, so a caller that builds per request cannot pile threads up. A caller that tests `corpus_ids()` alone sees the corpus missing as before; one that reads `failed_corpora` must accept a record with no path. Stuck workers are daemon threads.

- A hashed file now reports progress after its `lstat`, `open` and `fstat` as well as after each 64 KiB chunk, so a read that goes call by call is not mistaken for a stuck one.

A hop into a pending corpus, or one that failed on a root that did not answer, is declared in `routed_stale`. The ledger table pinned after boot is the one built from the registry the server booted from, never a re-read of the file.

### Changed (bounded root reads, slice 3 of `specs/38-bounded-root-reads.lts`: membership and the write rules)
- A write no longer resolves every registered root. Each root's real path is resolved by that root's own probe and kept with its last answer; root membership, the ledger's check that a ledger path lies outside every root, and `ledger.locate` read the kept path instead of resolving a root. A hung root therefore no longer stalls a write to a file under another root. The file being written is resolved as before. A write resolves a root in exactly one case, to confirm an attach: each ok candidate root (its kept path holds the file, or its declared spelling holds the path as typed) gets one bounded fresh realpath on an auxiliary slot of its own, never queued behind the root's poll and with at most one in flight per root; a confirm that gets no answer within the root deadline marks nothing and refuses the write `membership-unconfirmed` (a candidate that could hold the file, however it was typed), and a slow root whose every call answers is never late. A link swapped under a root while a server runs is seen by the next poll (about one second); until then kept paths only decide the refusal and which roots are candidates, and each ok candidate is confirmed as above, so a write's `corpora` is right in the window too (a write spelled through an ok root's own link attaches to the corpus the link now leads to). The write lands by its own real path. The refusal of a file under a marked root matches case-insensitively on every volume and folds Unicode composition (NFC) (a directory differing only in case is over-refused on a case-sensitive one). A `pathlib.Path` is accepted wherever a writer takes a path. A same-file stat that does not answer while a ledger's owner is judged is `old-location-unknown`, not 'another file'. A process with a kernel bounds these reads on the kernel's registry, so `stuck_workers` is the true count; idle auxiliary slots are pruned, and a slot first made auxiliary becomes a root again when a corpus registers on it.
- New refusal `root-unresponsive` for the five typed writers and `lts_add_node` with `create`: a file under a registered root that is pending or unresponsive is refused before the writer starts, so it neither waits for nor takes the per-file lock, reads nothing under the root and writes nothing. The reply names no path and no corpus and says what clears it. It joins the writers' stable refusal codes. A caller that treats an unknown refusal as an error needs no change; a caller that retries on a lock refusal should not retry on this one until the root answers.
- When the membership of a write is partial (a registered root is pending or unresponsive), the receipt (full and compact) and the ledger record carry `membership_partial: {marked_count, unconfirmed_count}` (`marked_count`: roots pending or unresponsive only; `unconfirmed_count`: candidates whose confirm did not answer, always 0 on a write that lands, since such a candidate refuses the write). Membership is evaluated once per write, so the record, the edge context and the receipt agree.

Retryable; nothing is written; the root is not marked; writes under other roots go on. A confirm never marks a root: at most one confirm per root is in flight; a write uses a confirm's answer only if that job began after the write's own file resolve (an older one is waited out), and joins one that began after. Any candidate root that could hold the file by its kept path or its declared spelling, however the file was typed, refuses the write when its confirm does not answer. The wait is bounded by no-progress time per disk call, at most the number of calls times the root deadline, and a write can wait for two confirms (a stale one, then its own). A corpus-omitted `lts_find`, `lts_find_in_prose` or `lts_reverse` leaves such a corpus out and says so in `extent.corpora_skipped` (`root-unresponsive`, or `root-pending`), with `complete: false` and `extent.index.fresh: false`; under a default scope `search_scope.stale_count` counts it.
- `lts_list_corpora` never waits on a marked root. Its entry has `fresh: false`, null `total_nodes`, `total_nodes_live`, `total_edges`, `resolved_edge_count` and `counts_agree` (null, not 0), and `root_health: {status, roots, since}`; a private corpus's `root_paths` is empty. The reply adds `stuck_workers` when above zero. With no slow root nothing in a reply changes.
- New stable codes: `root-unresponsive` (emitted now), `call-overran`, `engine-saturated`, `corpus-root-unresponsive` (pinned now, emitted by later slices). A caller that treats an unknown refusal `reason` as an error needs no change; a caller that retries on `stale` should not retry on `root-unresponsive` until the root answers.
- Known limitation: this slice bounds the freshness reads only, and a root is not marked until one deadline after its calls stop making progress. In that window (once per hang onset) a call that reaches the hung root (a read NAMING it, or a corpus-omitted read such as an unnamed `lts_find`, which probes every root first) holds the server's single request thread for the whole deadline, and every healthy read or listing queued behind it waits too. Measured, on a model of a hang: 2.71 s for a healthy read behind a named read on a 3 s deadline, and 0.43 s for an unnamed `lts_find` itself on a 0.4 s deadline; at the default 10 s deadline the wait would be about 10 s, which is an extrapolation from those and was not run. Calls on workers (slice 5) close it; until then it is a strict red record in the suite. A server still reads every root before its first request (a hung root at start stops the handshake), a write resolved every registered root at this slice (fixed by slice 3, above), and a call that reaches a root for the first time before any probe marked it can still wait on its disk. Those are the later slices of the same spec; do not put a root on an external drive in the start-up registry before they land.

### Changed
- Typed writers: a property value that is not a string is refused with `non_string_value`. `lts_add_node` used to store a list as the text `['a', 'b']`, and null as `None`, and report success; the other writers raised a raw `AttributeError`. A caller that sent a number or boolean to `lts_add_node` must now send a string. `lts_add_node` also refuses a `properties` that is not a mapping, null or absent (`bad_argument`, or `create_argument_invalid` on a create), which used to write a wrong property or an empty node. `lts_repair_property` with a null `value` still means take it from the line. On a create at an existing file, a non-string value is now reported first, ahead of `create_file_exists`. A non-string key, title or node id still raises an uncoded error, and writes nothing.
- `lts_add_node`: refusing an id that already exists now carries `evidence.refusal: duplicate_node_id`, and the query log records it. The reason text is unchanged.
- Named roots, write history (second part of `specs/36-named-roots.lts`): `factlattice.ledger.locate` is now the one way to a ledger path. After a move, `lts_history` also returns the ledgers written under the table's old spellings and the next write continues them. A root that declares a `state` location, with no marker, has its writes refused `state-unavailable`, and reads keep serving: the commands that begin a state location are parked, not scheduled (`specs/36-named-roots.lts`), so history stays in each machine's state folder and does not follow a corpus to another machine. Back up that folder with the corpus. `lts_history` now says "no ledger was found" with where it looked, and a file's first record says `new_chain`. A table field holding a NUL or text with no encoding is malformed; a tab or a newline in a path is taken. A malformed `named_roots` table (`named-roots-malformed`) now refuses every write outside the temp dir, because no location can be proved; a registry that cannot be read at all keeps today's behaviour; a state-rooted write is refused `named-root-state-unprovable` while any registry entry has failed or holds a root that cannot be resolved. A declared state that cannot be reached is `state-unavailable`, and one inside a corpus root is `named-root-state-inside-corpus`. Each refusal says what clears it in `evidence.fix`. A file under no root, in a registry with no table, keeps its ledger path and its record shape. `lts_history` no longer fails on a ledger line that is not a record or on a ledger it cannot read: it counts the line, or leaves the ledger out marked `history_partial`. A dangling link at a ledger's path reads as no ledger. Limit: a file created later at a moved file's old path takes that ledger as its own, including what the moved file wrote there, shown as a break.
- Named roots (first part of `specs/36-named-roots.lts`): a registry file may hold a top-level `named_roots` table, and a corpus entry's root path or profile may be written `${name}` or `${name}/relative`. Entries are expanded once when the registry is read, so every consumer sees absolute paths. `factlattice.registry.resolved_entries(path)` and `python -m factlattice_engine registry resolved --file <path>` are the public way to read a registry from outside the engine. A registry with no table and no `~` or relative root reads exactly as before. A `~` profile path now expands too.
- Upgrade note: a tool that parses a registry file itself meets a new top-level key with no `roots`, and `${name}` paths. Move it to `resolved_entries` before a registry adopts the table. An engine older than this lists `named_roots` as a failed corpus, and reads `${name}/x` as a missing path, so rolling the engine back restores the prior registry too.
- Reviewer `resolve-output`: while any registry entry has failed on an unknown key or a named root, every document is refused with that code, not only one found inside the entry. A scan of a failed entry's strings could not be complete. A clean private entry none of whose roots can be read refuses too (`private-corpus-location-unknown`), so a private corpus on an unmounted drive stops every review of every corpus until it returns; one readable root is enough to avoid this. `lts_report_miss` answers `corpus-roots-unknown` while any corpus has failed to build. Other engine tools keep serving the healthy corpora.
- A relative root path in a registry file now resolves against the registry file's directory (or `FACTLATTICE_CORPUS_ROOT`), no longer the process working directory. A relative profile path keeps its existing rule.
- `lts_list_corpora`: a corpus whose every root is missing is listed with `root_health.status: no-roots` and zero nodes instead of vanishing (a private one is counted in `private_failed`). A registered profile at a missing path is reported in `missing_roots` with reason `profile-missing`.
- `lts_find`: an item larger than `token_budget` is now skipped and reported in `oversize_skipped`, not sent whole. Each entry gives the item's id, title, size, and how to read it: its identity and edges with `lts_node(..., tier='digest')`; all its properties with `lts_node(...)`, or this call again with `token_budget` at least the item's size (that read is the item's full size, and no budget makes it smaller). The rest of the page still fills with the items that fit, and `truncated` is true. Before this change, a single very large item was always returned whole, however small the budget. That could overflow a client and push smaller matches to a later page. This applies to calls with no `tier` as well. It is the one deliberate exception to "omitting `tier` gives the pre-tier behaviour", because the old behaviour contradicted the budget rule in the specification ("an over-budget item is skipped whole and reported").
- Aggregations (`lts_aggregate`, profile audits) and the reviewer's self-gate and site-config lookup still read every match: they fetch with an unbounded budget, and they return an error (or fail the gate) rather than work around a skipped item.
- Registry keys are now validated where a corpus is built. One schema (`factlattice.registry.REGISTRY_ENTRY_KEYS` and `REGISTRY_ROOT_KEYS`) lists the keys a registry entry and a registry root may carry; a key ending in lowercase `_note` is free text and is never refused. An unknown key (for example a misspelt `private`, `profile`, `domain_suffix`, `roots` or `path`) now fails only the corpus that carries it, with the code `registry-entry-unknown-key` or `registry-root-unknown-key`, naming the key and the nearest valid key; every other corpus keeps serving. Before this change such a key was accepted and its setting silently absent, and a bad root key stopped the whole registry from loading. A corpus whose unknown key is `private` or a near-miss of it counts as private (it is counted, not named, on a call that names no corpus). `lts_list_corpora`, `extent.corpora_skipped`, `lts_register_corpus`, the reviewer helpers (including `resolve-output`) and the contradiction checker apply the same rule.
- Upgrade note: a registry that holds other free-text keys will see those corpora refused, loudly, at its first start after upgrading. Rename each such key so that it ends in `_note`.

### Fixed
- A read that began after a write could be answered from before it, with `success: true` and `fresh: true`, until the next change to the corpus. Seven caches were filed under the freshness key (the kernel's maintained root, which moves when a file changes) but built from `Partition.nodes` or `.layers`, which change only when the heal publishes. A reader that had passed its gate and reached a cache in between built it from the old content under the new key, and the key matched again after the heal. The answer can be a miss (`lts_find_in_prose` count 0 for a token present in the nodes; `lts_reverse` without a new referrer) or stale non-zero (`lts_reverse` still reporting an edge that was deleted). Affected: the body index, the reverse index (also `include_reverse_digest`), the structural-find field caches (`all_of`/`any_of`/`none_of`, prefix vocabulary), the relevance-rank cache, the semantic service's card state, and, only when a build straddled the heal, the adjacency map (`lts_node`, `lts_traverse`, `lts_flow`) and the degree index (`lts_aggregate`). Each cache now records the object it was built from, builds from one read of it, and is served only while that object is current; no new lock. Rate: in a nine-thread in-process run (three writers, six readers, `tools/cache_freshness_stress.py`), 1010 of 13,500 follow-up reads by the writers were wrong on the unfixed code (1 in 13; six runs on a 12-core machine, load average about 14 to 16 where it was printed, not recorded for each run): 313 of 6,750 (4.6%) in the three runs with no added delay, 697 of 6,750 (10.3%) in the three with a sleep of up to 3 ms between the gate and the cache. An independent run reproduced 1 in 12 at load 14 to 17, and 245 of 4,500 (5.4%) with no sleep. None after the fix. This is not a server exposure rate. The server has one request thread and a watcher; the gate-to-key window is about a microsecond for prose, field find and reverse, and about 2 ms for rank. A run shaped like the server on the unfixed code found no wrong answer in about 579 writes across two readers, which bounds the rate only below about 1 in 190 at 95% confidence. The stress tool states its limits.
- A root path starting `~` in a registry file now loads; it used to fail at build, leaving the corpus out.
- Reviewer `resolve-output`: a document inside a private corpus nested in the named corpus's root used to be routed by the named corpus's rules, so it could take the shared default root. Every registered corpus containing the document is now checked; a private container refuses with `document-in-private-corpus` unless an override keyed to that private corpus routes it. A private corpus named directly behaves as before.
- API break: `factlattice_engine.reviewer.resolve_output` now requires the keyword-only argument `all_corpora` (the registry's id -> spec mapping; `None` or a non-mapping raises `TypeError`). Out-of-tree callers must pass it. `frame --exclude-source` now also works for corpora registered with the single-`root` shape.

### Known limitation
- Other tools that apply a token budget (`lts_traverse`, `lts_capabilities`, `lts_flow`, `lts_reverse`, edge paging in `lts_node`, the page path of `lts_find_in_prose`, `lts_lint`) still return an over-budget item whole. They will follow.
