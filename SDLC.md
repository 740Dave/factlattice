# FactLattice Software Development Lifecycle

> The complete workflow from spec authoring through deployment, with quality gates, maintenance cycles, session hygiene, and the Architect dispatch orchestration model. Specs are the delegation substrate. Every tool exists to make specs more accurate, implementations more correct, and quality gates more rigorous.

---

## 1. Lifecycle Overview

```
                    ┌─────────────────────────────────────────────┐
                    │           SPEC AUTHORING                     │
                    │  spec editor → factlattice-linter → spec     │
                    └──────────────────┬──────────────────────────┘
                                       │
                    ┌──────────────────▼──────────────────────────┐
                    │    ARCHITECT DISPATCH (with orchestration)    │
                    │  Architect sets: build + adjacent agent flags │
                    │  security_review? code_quality? when?        │
                    └──────────────────┬──────────────────────────┘
                                       │
                    ┌──────────────────▼──────────────────────────┐
                    │           BUILD + ORCHESTRATION               │
                    │  Builder receives dispatch, invokes flagged   │
                    │  agents (before/after build), builds to spec  │
                    └──────────────────┬──────────────────────────┘
                                       │
                    ┌──────────────────▼──────────────────────────┐
                    │           FIRST BRINGUP                      │
                    │  Launch, crash, fix, repeat until it runs    │
                    └──────────────────┬──────────────────────────┘
                                       │
                    ┌──────────────────▼──────────────────────────┐
                    │           QUALITY GATE (Review)              │
                    │  factlattice-gap-analyzer → findings → fix       │
                    │  → Architect evaluates → accept or re-dispatch│
                    └──────────────────┬──────────────────────────┘
                                       │
                    ┌──────────────────▼──────────────────────────┐
                    │           DEPLOY                             │
                    │  Deploy, verify, document                    │
                    └──────────────────┬──────────────────────────┘
                                       │
                    ┌──────────────────▼──────────────────────────┐
                    │           MAINTAIN                            │
                    │  factlattice-densifier → signal-loss-reviewer    │
                    │  factlattice-corpus-analyzer (end of session)     │
                    └─────────────────────────────────────────────┘
```

### Context Defense

This lifecycle is maximally defensive of the main conversation's token budget. Every specialized agent runs in its own context window. The Architect stays at the design level: writing specs, reviewing reports, making decisions. Execution is always delegated. A session that manually debugs, tests, and deploys burns ~300K tokens on mechanical work. The same session with proper delegation burns ~10K tokens on dispatch and review.

## 2. The Review Model

The core quality assurance pattern. The Architect designs, the Builder builds, the analyzer audits cold, the Architect evaluates. The Architect MUST NOT review code directly — confirmation bias applies to infrastructure code as much as product code.

```
Architect (spec) → Builder (implement) → Gap Analyzer (audit cold) → Architect (evaluate)
     ↑                                                                       |
     └────────────────── close gaps or accept as-designed ──────────────────┘
```

### Enhanced Review with Orchestration

The Architect's dispatch carries orchestration flags that tell the Builder which adjacent agents to invoke and when:

```
Architect dispatch:
  spec: path/to/spec.lts
  build: true
  adjacent_agents:
    - agent: security_review
      when: before_build
      scope: "Crypto key handling, auth boundary"
    - agent: code_quality
      when: after_build
      scope: "New module, verify test coverage"
```

The Architect decides WHAT to invoke. The Builder orchestrates the invocations. The Builder may recommend ("this touched auth code I didn't expect — suggest security review") but does not unilaterally expand scope.

## 3. Architect Dispatch Format

### 3.1 Dispatch Structure

Every dispatch from Architect to Builder carries:

| Field | Required | Description |
|-------|----------|-------------|
| `spec` | Yes | Path to the linted spec |
| `build` | Yes | Whether to implement (always true for build dispatches) |
| `adjacent_agents` | No | List of agents to invoke alongside the build |
| `priority` | No | Relative urgency |
| `scope_notes` | No | What to focus on, what to skip |

### 3.2 Adjacent Agent Timing

| Timing | When to Use | Example |
|--------|-------------|---------|
| `before_build` | Review the DESIGN before implementation begins | Security review of crypto spec before Builder writes signing code |
| `after_build` | Review the CODE after implementation | Code quality audit of a major refactor |
| `both` | Bookend the build — design review first, implementation review after | High-risk crypto + auth work |

### 3.3 Decision Heuristics

The Architect decides which adjacent agents to flag based on the nature of the work:

| Work Type | Adjacent Agents | Timing |
|-----------|----------------|--------|
| Normal feature work | None | — |
| Touches crypto/auth/access control | `security_review` | `before_build` |
| Major refactor (3+ modules) | `code_quality` | `after_build` |
| New cryptographic protocol | `security_review` | `both` |
| Performance-sensitive path | `performance_analysis` | `after_build` |
| Data migration / schema change | `security_review` + `code_quality` | `before_build` + `after_build` |

### 3.4 Builder as Orchestrator

The Builder receives the dispatch and orchestrates execution:

```
1. Read dispatch flags
2. If before_build agents flagged:
   a. Invoke each flagged agent against the SPEC (not code — code doesn't exist yet)
   b. If findings: report to Architect, await decision (proceed / revise spec / abort)
3. Build to spec
4. If after_build agents flagged:
   a. Invoke each flagged agent against the IMPLEMENTATION
   b. Fix findings within Builder's authority (mechanical fixes)
   c. Report remaining findings to Architect
5. Report build complete
```

The Builder orchestrates ephemeral agents — they spin up, do their work, report findings, and terminate. The Builder manages the lifecycle; the Architect manages the decisions.

### 3.5 Normally False, Callable on Judgment

Most dispatches carry no adjacent agent flags. The independent review's gap analyzer is the default quality gate. Adjacent agents are invoked when the Architect's judgment says the work warrants it. This avoids adding latency to every cycle while ensuring high-risk work gets proportional scrutiny.

## 4. Stage 1: Spec Authoring

### 4.1 Writing Specs

Specs are written in FactLattice format (`.lts` files). They are the authoritative source for all implementation work. A spec that doesn't exist means the feature doesn't get built. A spec with ambiguities means the builder guesses.

| Tool | When | Purpose |
|------|------|---------|
| **spec editor** (a deployment-provided editing agent; not shipped here) | Creating or modifying .lts files | Structured edits with automatic post-edit linting. Domain-profile-aware. |
| Intelligence authoring | New specs from scratch | Author interactively, then lint. Humans MUST NOT edit .lts files directly. |

### 4.2 Linting Specs

**Every spec MUST be linted before it is used as a build input.**

| Tool | When | Purpose |
|------|------|---------|
| **factlattice-linter** | After every write/edit, before dispatching to builders | Validates structure, reference integrity, namespace resolution, confidence annotations, language density. Loads domain profile at runtime. |

### 4.3 Integration Spec Pattern

When specifying an integration between two systems:

1. **Spec the external system** as a FactLattice document. Research actual APIs, not training data.
2. **Write the integration spec** referencing both systems via cross-domain references.
3. **Triangulate**: dispatch an analyzer that cross-checks every claim in the integration spec against both authoritative spec sets.
4. **Fix triangulation findings**, then lint.

---

## 5. Stage 2: Build

### 5.1 Dispatching Builders

Builders are ephemeral agents that receive a linted spec (with orchestration flags) and produce implementation files. The spec is their complete requirement.

| Principle | Rationale |
|-----------|-----------|
| One spec per builder | Focused scope. Parallel builders for independent specs. |
| Spec reference in prompt | Always include the spec file path. Builder reads it first. |
| No phasing by velocity | Build everything the spec describes in one pass. |
| Context conservation | Builders get their own context windows. Delegate execution. |

### 5.2 Parallel Builds

Independent specs produce independent builds. Dispatch simultaneously:

```
spec-A (module X) ──→ builder-1 ──→ module_x/
spec-B (module Y) ──→ builder-2 ──→ module_y/
spec-C (module Z) ──→ builder-3 ──→ module_z/
```

Integration bugs between parallel builds are caught at the quality gate stage.

---

## 6. Stage 3: First Bringup

Static analysis cannot find runtime integration bugs. First bringup is the "run it and fix every crash" stage.

| Principle | Rationale |
|-----------|-----------|
| Offline first | Test rendering/logic before transport. Isolate failure domains. |
| Fix in place | The bringup agent fixes bugs directly — no round-trip to the Architect for mechanical fixes. |
| Expect 3-15 bugs | Clean gap analysis does not mean zero runtime bugs. |
| Report visual unknowns | The agent cannot judge "does this look right." List what needs human eyes. |

---

## 7. Stage 4: Quality Gate (Review)

### 7.1 Dynamic Composition

The quality gate is not monolithic. Dimensions run individually or in combination:

| Pattern | When | Sequence |
|---------|------|----------|
| Iterative fix | Normal development | gap-analyze → fix → verify → next dimension |
| Full gate | Pre-deploy | All dimensions in parallel → unified assessment |
| Targeted | Known risk area | Single dimension (e.g., security-only for auth changes) |

**Run a dimension, fix what it finds, then run the next.** Each fix may resolve findings in other dimensions.

### 7.2 Dimensions

| Dimension | Agent | Input | Output | Trigger |
|-----------|-------|-------|--------|---------|
| Spec-Gap | `factlattice-gap-analyzer` | Spec + implementation | Gap list with IDs, severity, references | Every build (mandatory) |
| Security | General-purpose with security scope | Implementation + spec | Findings with CWE reference | Architect flag on dispatch |
| Test Coverage | General-purpose with QA scope | Implementation + spec + tests | Coverage assessment, missing tests | When independent tests needed |
| Context Economy | General-purpose | Implementation, MCP tools | Per-call cost table, growth projections | When touching context-sensitive paths |
| Code Quality | `factlattice-code-quality-auditor` | Implementation | Quality findings, debt assessment | Architect flag OR nightly scheduled sweep |

### 7.3 Code Quality: Two Modes

The code quality auditor operates in two modes:

- **On-demand** (Architect-flagged): Builder invokes during build for major refactors or critical paths. Findings are immediate and actionable.
- **Scheduled** (nightly sweep): Runs on a schedule, sweeps the full codebase, catches quality drift over time. Findings go to the quality event stream. Doesn't block any build cycle.

The nightly sweep catches what inline review misses — gradual debt accumulation, inconsistent patterns across modules, test coverage erosion. It's the long-term health monitor.

### 7.4 Deployment Decision

| Condition | Decision |
|-----------|----------|
| Any unresolved P0 | **BLOCK** |
| All P0s resolved, P1s exist | **CLEAR WITH CONDITIONS** |
| No P0s, no P1s | **CLEAR** |
| Architect override with rationale | **Permitted** |

### 7.5 Standing Check: New Multi-Corpus Reads

Any change that reads more than one corpus, or follows an edge into another corpus, must state how it treats PRIVATE corpora (`[INV-PRIVATE-FANOUT]` in `specs/20-engine-layers.lts`), and the review checks that statement:

- A corpus-omitted read goes through `_fanout_parts` / `is_private_partition`, never a raw `store.partitions()` / `store.corpus_ids()` loop.
- A cross-corpus hop passes the origin corpus to `_route`, and a withheld hop is declared in `routed_withheld`, never dropped silently.
- Every new touch of the corpus collection is added to `FANOUT_ALLOWLIST` in `tests/test_private_corpus_fanout.py` with its reason.

That test is a TRIPWIRE, not enforcement: it catches the ordinary way fan-out code gets written, not `getattr`-by-string or iteration of a list a helper already returned. This checklist line is the belt beside it; the review is the braces.


### 7.6 FACTLATTICE-SPEC-CHECKLIST: Extension Points Every Engine Change Must Honour <a id="factlattice-spec-checklist"></a>

Owners: the engine maintainers, jointly (2026-10-02). Seeded from the 2026-10-02 reviews: privacy F-E3, semantic S1-S4 F11, S5 F4, delta F-D6. Renamed from FL-SPEC-CHECKLIST on 2026-10-03 to avoid a name clash with an unrelated checklist in a downstream deployment. **The review checks each applicable line**; a change that adds a NEW extension point adds its rule here in the same commit.

**Privacy**
- [ ] A new corpus-omitted read, or a new cross-corpus hop, states its privacy decision (§7.5; `[INV-PRIVATE-FANOUT]`), and its touches of the corpus collection are in `FANOUT_ALLOWLIST` with a reason.
- [ ] [ISSUE-PRIVATE-NAMES-IN-ERRORS] No error, suggestion or extent field may NAME a private corpus: not `_not_found`'s list or did-you-mean, not `extent.corpora_available`, not `extent.corpora_skipped` (one anonymous `{reason, count}` entry), not `stale_corpora`, not a tool's `available` list, not a `routed_withheld` stub (anonymous `{withheld, reason}`: no corpus id, no target id), and a stale private corpus is an anonymous `private_stale_count`, never a name (keeping `complete` and `index.fresh` consistent). Names come from `LtsEngine._public_corpus_ids()` only, and the error carries the one line `private corpora are searched only when named exactly`. A private corpus appears only when the caller named it exactly (or in `lts_list_corpora`, the explicit enumeration surface). `tests/test_private_names_never_leak.py` enumerates `server.TOOLS` and deep-scans every response, so a new corpus-gated tool is covered automatically; a new error path that names corpora must pass through that test.

**Exact answers stay exact** (`[DEC-SEMANTIC-ASSIST]`)
- [ ] Semantic or suggestion output never enters `nodes`, `digest`, `count`, `total_matched`, `truncated` or `complete`; it lives only in its own labelled block, with `is_assertion: false`.
- [ ] Every new INTERNAL caller of `LtsEngine.find` passes `semantic="off"` (the env switch must never reach analytics, lint or authoring).
- [ ] A `rank` mode only re-orders: the match set and `total_matched` are invariant, and ordering is applied BEFORE paging.

**Models, weights, indexes**
- [ ] Model weights are sha256-pinned in `semantic/embedder.py:PINS` and loaded offline; no code path opens a network connection (tests deny sockets).
- [ ] The core engine imports no model stack: numpy and onnxruntime are imported lazily, inside the semantic layer only (a test asserts it).
- [ ] Any change to `semantic/cards.py` bumps `CARD_SCHEMA_VERSION`; any change to `semantic/tokenizer.py` bumps `TOKENIZER_VERSION`. `index_version` (`semantic/index.py:_version_material`) covers the model, card schema, chunking, chunk penalty, tokenizer version, embedder version (`EMBEDDER_VERSION`, bumped on any change to `Embedder.embed`/`plan`/`run_batch` that can move a bit of a vector; a byte-identical refactor, shown by a test against the previous loop, does NOT bump it, since a bump orphans every sidecar), vocab sha, pooling, query/doc prefix, max_len, dimension, the Unicode table version (`unicodedata.unidata_version`), the onnxruntime and numpy versions and the stored vector dtype (`STORAGE_DTYPE`); a sidecar built under any other value is refused, never mixed. A new vector-shaping parameter is added to `_version_material` in the same commit.
- [ ] Sidecar writers hold the per-sidecar `.lock`, write via unique temp names + rename, and write the manifest LAST, pinning the vectors' sha256. Every directory on the sidecar path (`semantic/`, `semantic/<model>/`, `v-<index_version>/`, the corpus leaf) is 0700, so private corpus names are not listable. Each index_version has its OWN dir ([SIDECAR-PER-VERSION]): code must never rebuild or delete another version's sidecar in place, except the lock-guarded, age-gated GC (`GC_AGE_S`), so engines of two versions can run side by side during a go-live. Lock order is the sidecar's OWN `.lock` first, then another dir's (the legacy dir on adoption, never blocking on a GC target: `LOCK_NB`); never the reverse, so no cycle is possible. GC never follows a symlink out of `semantic/<model>/` and re-checks the age once it holds the lock.
- [ ] [MECH-SEMANTIC-EMBEDD] `LTS_SEMANTIC_EMBEDDER=shared` routes embeddings to one per-user service (`semantic/embedd.py`); `local` (default) is unchanged. `Embedder.plan`/`run_batch` are `Embedder.embed` (the EMBEDDER_VERSION rule applies to them); the service runs the same plan, so vectors stay byte-identical. Every embed call site handles `SemanticUnavailable` as a labelled status (a down, stalled, refused or mismatched service is never an exception into a caller and never a hang). The service's run dir, socket and pidfile are refused when symlinked or not owned by this euid; peers are checked by kernel credentials. Its log must never carry request text: an exception raised or logged under `_serve_conn` must not interpolate texts (the service logs lifecycle lines, one line per malformed request and internal-fault tracebacks only). Its state root must not sit in a world-writable directory without the sticky bit (parent components are not walked).
- [ ] [MECH-EMBEDD-ALWAYS-ON] The always-on service (`embedd keep`, LaunchAgent `io.factlattice.lts-embedd`; `launchagent install` migrates an earlier-release agent only when its plist is `<label>.plist`, its Label ends `.lts-embedd`, and its content equals the plist this install would write apart from Label; a differing same-module agent is left alone unless named with `--adopt-legacy`. It boots the old label out BEFORE bootstrapping the new one (a bootout that fails with the agent still loaded stops the install), removes the old plist only after the new bootstrap succeeds (a failed unlink exits non-zero), restores and reports the old agent on any failure in between, refuses a symlinked, non-regular or unreadable legacy-shaped file, and never touches another plist; `launchagent status` reports leftovers. Limit: a loaded agent whose plist is already gone is not found) must restart whenever anything that shapes the material changes, or two resident models result. (1) A file added to `factlattice_engine/semantic` that shapes vectors or pin resolution joins `KEEP_SOURCE_FILES` in the same change. (2) `watch_fingerprint` also covers what no source edit shows: the onnxruntime and numpy versions (read fresh each tick), the interpreter's realpath + mtime + size (it carries the Unicode table) and the content of `LTS_SEMANTIC_PIN_FILE`; a new environment input to `_version_material` is added to it, with a test that it alone triggers exit 75. (3) The plist keys (Label, ProgramArguments, EnvironmentVariables copied from the lts-engine MCP entry, RunAtLoad, KeepAlive SuccessfulExit false, ThrottleInterval, log paths) are generated only by `launchagent install` and stay as the spec's `launchd` and `install-environment` properties say; a new material-shaping env key joins `MCP_ENV_KEYS`. (4) `<run>/embedd-keep-starts.json` is written 0600, via a uniquely named temp file unlinked on failure, never through a symlink, and a failure to write it must exit 0, never into a restart loop; every start, including a refusal, is counted BEFORE anything that can refuse. (5) `<run>/embedd-keep-tripped.json` (the durable tripped marker `status` reads) is written 0600, never through a symlink, with the reason (`crash-loop` or `uncountable:`), and is cleared ONLY by the `Server.on_ready` hook (bound and serving), never by a mere start or a wait. A new durable state file beside it follows the same rules.
- [ ] [QUERY-REPORT-MISS] Any NEW file a tool writes into the state dir (`querylog.state_dir()`, e.g. `miss-log.jsonl`) is root-guarded: the resolved path is compared with every registered corpus root with normalised paths (realpath, case folding, and st_dev/st_ino ancestry, so case variants and symlinks cannot bypass it), it is never written inside a corpus root, and a refusal names no path, corpus or root (it may be private). A tool that gathers its evidence by calling other searches surfaces each search's status in its response and record (`exact_status`, `semantic_status`), so a failed search never reads as "not found". Status text is a fixed vocabulary (ok, unavailable, index_building, `error: digest ceiling exceeded`, `error: <ExceptionClassName>`, where the class name is used only if it matches `^[A-Za-z_][A-Za-z0-9_]*$`, else `Exception`, because a class can be created with any `__name__`): never raw or sanitised exception text, because a path in any form (relative, spaced, `~user`, a bare directory name) can identify a private corpus; detail goes to the stderr log only. The root guard fails closed: if the registered roots are unknown, or the list holds an empty or blank root (which would normalise to the working directory), nothing is written.
- [ ] Every index failure state is REPORTED, never an exception into a caller and never "building" forever: as a `status` (`unavailable`, `index_building`, `index_failed`) or, when a stale index is still served, as a `refresh_failed` reason beside `status: "ok"`; retries are cooled down.
- [ ] Derived per-corpus caches are keyed on the partition's `_freshness_key()` and LRU-bounded: the engine's BM25 cache (`LEXRANK_CACHE_MAX`) and the semantic service's card/BM25 state and index objects (`SemanticService(cache_max=...)`).

**Parser findings**
- [ ] An `undeclared_key` ParseFinding may be LAZY (`parser._UndeclaredKeyFinding`): its `message`/`detail` (the did-you-mean suggestions) are computed on first read, so plain parsing pays nothing ([PERF-LAZY-KEY-SUGGEST]). Code reading findings goes through attributes, `to_dict()`, `==`, `dataclasses.asdict`/`replace`. It never relies on `vars(f)`/`f.__dict__` or `type(f) is ParseFinding`, and never reads findings eagerly on the build path (a test pins 0 suggestion computations per parse).

**Process lifecycle (re-exec)**
- [ ] [INV-RECONCILE-SERVES / STDIN-CARRY] Any code path that re-execs the server (today only `build_stamp.reconcile_by_reexec`) holds `SERVING_LOCK` and CARRIES PENDING INPUT to its successor the same way. Carried: the incomplete trailing request line `serve()` has already read off stdin (complete lines are always answered before the lock is released; unread bytes stay in the kernel pipe, which survives exec). Transport: a file `carry-<token>` (token = 32 random hex) in `<engine state root>/carry/` (`querylog.state_dir()`; created 0700, owned by the running uid, never under TMPDIR), mode 0600, written `O_CREAT|O_EXCL` through a directory fd; the env carries only its PATH (`FACTLATTICE_STDIN_CARRY`) and the TOKEN (`FACTLATTICE_STDIN_CARRY_TOKEN`), never the bytes. The successor takes it BEFORE `build_tools()` starts the sentinel and accepts it only if: the path's directory is exactly the carry root; the name is `carry-<token>` with the token from the second env var; the dir, opened `O_DIRECTORY|O_NOFOLLOW`, is a directory, ours, mode 0700; the file, opened relative to that dir fd with `O_NOFOLLOW|O_NONBLOCK`, is (by `fstat` on the fd) a regular file, ours, mode 0600, `st_nlink == 1`. It then unlinks that exact name via the dir fd, only if it is still the same inode. Anything else is refused with a warning that names the value only by length and short sha256, never raw text. A failed `execv` removes the file and both vars (the old process keeps serving; later subprocesses are not poisoned). At startup `serve()` sweeps `carry-*` regular files we own older than 10 minutes, via the validated dir fd. Any new stdin reader or re-exec path goes through `_iter_requests` / this carry; an unterminated final line at EOF is still answered. Each guard has its own test in `tests/test_code_currency_reconcile.py` (`test_guard_*`, `test_sweep_*`).

**Corpus writes** ([ISSUE-WRITE-ATOMICITY])
- [ ] Every code path that writes a corpus file is ATOMIC, takes the PER-FILE LOCK and is COMPARE-AND-SWAPPED. A new writer (a verb, the clerk's replay, split/move) MUST use the shared write step in `factlattice/authoring/edit.py`: decorate with `_serialised` (exclusive `fcntl.flock` on a sidecar in the engine STATE dir, never the corpus dir, keyed on the REALPATH, held across read -> gate -> write; bounded wait; "busy, retry" refusal; a filesystem that cannot flock refuses at once), read the file with `_read_base` INSIDE the lock (it records the exact bytes the candidate is computed from), and write through `_write` (preflight refusals: not writable, hard-linked; backup; temp in the real path's directory, never `*.lts`; fsync; owner/xattrs/mode copied; mtime refreshed; CAS of the on-disk bytes against the base immediately before `os.replace`, so a writer OUTSIDE the lock, such as an old engine, a hand edit or a sync client, is refused rather than overwritten). A whole-document writer uses `write_whole_file`. Residual window: the CAS and `os.replace` are two syscalls, so an outside write landing between them is still lost; the lock closes it for every writer that takes the lock. A direct `write_text`/`open(..., "w")` in `factlattice/authoring` fails `tests/test_atomic_write_round2.py::test_no_authoring_module_writes_a_corpus_file_directly`. Proof for a new writer: a >=30-round multi-process lost-update test and a real-SIGKILL test (`tests/test_atomic_write_lock.py`, `tests/test_atomic_write_round2.py`).

- [ ] [NODE-CHANGE-LEDGER] Every applied corpus write appends ONE hash-chained record to the per-file ledger (`factlattice/ledger.py`, `<state_dir>/ledger/<sha256(realpath)[:32]>.jsonl`, dir 0700, file 0600), INSIDE the per-file lock, right after `os.replace`, in the one shared step: a new writer passes a `ctx` (verb, node_id, key, delta, discarded, plus the `_meta(...)` audit fields) to `_write`, or goes through `write_whole_file`; it never calls `_atomic_replace` on its own. A new writer verb is added to the ledger spec's verb list and gets an L1-style test (one record, every field, delta/discarded equal to its receipt), plus an undo-from-`discarded` test if it removes or replaces anything. A refusal appends nothing. A ledger failure after the write is `ledger: {status: "failed"}` on the receipt and a "WRITTEN, BUT NOT LEDGERED" lead on the report, never silent. The ledger path is refused inside any registered corpus root (L8; the engine adapter injects the roots, since `factlattice` cannot see the registry). `tests/test_node_change_ledger.py::test_F8_every_public_writer_appends_exactly_one_record` pins it behaviourally (writers found by introspection; a writer with no ledger record fails). Append, add_node and a new-key set record `inserted {line_number, lines}` so every verb is undoable from the record.

- [ ] [LEDGER-NO-DIRECT-WRITES] A script that changes a corpus file goes through the typed writers or `write_whole_file` (as a library call or over MCP); both append a ledger record. A direct file write (`open().write`, `write_text`, an editor) is NOT recorded and surfaces only as a chain break (`chain_file_breaks`, and the receipt warning "OUT-OF-BAND EDIT" on the next write); it is a checklist violation.
- [ ] [INTERIM-WRITER-EXPECT-BASE] An interim corpus writer under tools/ (retitle_gated, set_list_item_gated) reads the file once as bytes, gates on that text, and writes ONLY via write_whole_file(..., expect_base=<those bytes>), so the bytes it gated are re-checked under the per-file lock. A tools/ writer without expect_base is a lost-update bug (review P1-1, 2026-10-04).
- [ ] [LEDGER-UNDO-EVIDENCE-DURABLE] The UNDO EVIDENCE for every write outlives the audit period: for typed writers, the ledger record (discarded/inserted, byte-exact); for whole-file writes, the prior file content is kept durably and content-addressed (`<state_dir>/ledger-blobs/<sha256>`, referenced by the record's `prior_blob`). $TMPDIR backups are a convenience, not evidence: the OS cleaner removes them (measured 2026-10-04: 47,762 backups covering only 4 days).
- [ ] [LEDGER-SCRATCH-COPIES] A scratch or preflight copy of a corpus file belongs in the OS temp dir, where a write is EPHEMERAL and the ledger skips it with `ledger: {status: "skipped"}` (`ledger.is_ephemeral`); once the writers gain dry_run (design note v1.1 D3; not yet built), a preflight should use that instead of a scratch copy. An AST TRIPWIRE (`tests/test_nonregular_round3.py` proves it fires on a raw open planted in scratch copies of tools.py, store.py, semantic/index.py and reviewer/__init__.py) fails on a new raw site (a tripwire only: it sees literal call forms, including `os.open` read-only, `X.open`, `shutil.copy*`, `np.load`, aliases and from-imports, each with a planted case; its test docstring lists what it does NOT see, and states that a NEW raw read added inside any EXEMPTED function stays green (exemptions are per function name; those functions are covered by review, not by the scan; NOT covered by a per-function check): variable-held functions, `ctypes`/C extensions, `mmap`, subprocess, `json.load(fh)` on someone else's handle, write-mode opens). (2) every fan-out (a tool that can run corpus-OMITTED) reports the corpora it could not read: `extent.corpora_skipped` / `corpora_skipped` entries `{corpus, reason: <code>}`, and a failed PRIVATE corpus is only COUNTED (`{reason: private-corpus-failed, count}`, `private_failed`), never named, on an unnamed call ([INV-PRIVATE-FANOUT]). A new corpus-optional tool must be added to the fan-out test (driven from the tool list: it fails on an undecided tool). (3) the failure is typed: `CorpusFileError(OSError)`, `code` in `CORPUS_FILE_CODES` (`corpus-file-not-regular`, `corpus-file-broken-link`, `corpus-file-unreadable`, `corpus-dir-unreadable`), ROOT-RELATIVE `rel_path` only, so `str(exc)` is persistable ([REGISTRY-PATH-SURFACES]); it fails only its own corpus (`config.build_store` -> `store.failed_corpora[cid] = {code, path, private}`), is never `registry-not-found`, and is never a partial view ([INV-LTS-FRESH] GAP-1): a corpus-scoped tool answers `success: false, reason: <code>, error_class: CorpusFileError, corpus, path`; `lts_list_corpora` carries `failed_corpora`; path-mode tools (`lts_lint`, `lts_preview` of a directory, `lts_property_loss`) answer the same shape without `corpus`, while the three typed writers answer their usual `refused: true` reply with `reason` = the code, `error_class: CorpusFileError`, `evidence.refusal` = the code and a basename-only `path` (a single-file `lts_lint source=` / `lts_preview path=` of a special file is NOT coded: it answers a plain not-found text); the freshness CLI, the lint CLI and the reviewer helpers (`HELPER_REASON_CODES`) name the code. (4) AFTER BOOT the freshness kernel fails closed: a member that turns unreadable (the stat hint carries the permission bits) or a new unreadable member empties that root's leaves (STALE, never fresh over old content) and the self-heal reports the code; one bad corpus never stops the others from being polled. Pinned by `tests/test_nonregular_file_in_root.py` and `tests/test_nonregular_round2.py` (hang-prone cases run in a child with a hard timeout; special files only under a scratch root). (5) THE KERNEL FAULT LIFECYCLE (`RootState.fault` in `factlattice_engine/kernel.py`): it is SET when a hash of a member raises (any OSError; a coded `CorpusFileError` keeps its code, anything else is `corpus-file-unreadable`) and it EMPTIES the root's leaves, so the corpus is stale while it is set (never a quiet 'unchanged' over old leaves); it is cleared when (a) a full re-hash of the root succeeds (`_reload_root_full`, the self-heal, the backstop), (b) the bad member left the listing, or (c) a hash of the bad member succeeds (one file per tick), because a cause such as an ACL can come and go without moving mtime, size or mode. A fault must never outlive its cause, or edits to OTHER members are hidden. Every hash that records a stat hint takes the hint BEFORE the hash and re-checks it after (`_hash_stable`; a member that moves three times in a row is unverifiable and fails closed). (6) THE OSError-TO-CODE MAPPING (`hashing._io_error`): at classify, open, fstat and read time an OSError that is not name-gone (FileNotFoundError, NotADirectoryError, IsADirectoryError) becomes `corpus-file-unreadable`; name-gone stays distinct at the member level (the kernel collapses it, deliberately, to fail closed), and an OSError while LISTING a directory (not a vanished one) is `corpus-dir-unreadable`, so one corpus fails and never the registry. (7) THE WRITER PRE-CHECK GATE (`tools._writer_target_error`): before a typed writer runs, the target is classified (`check_member` plus a read-access test); it must NEVER raise (it sits outside the writers' own exception net: any failure returns None and the writer codes it), a missing path or a directory keeps the writer's own message, and it has a stated CHECK-THEN-USE WINDOW: if the kind of the file changes between the pre-check and the open, the writer gives its old uncoded reply, never a hang (the open is O_NONBLOCK) and never a write to a non-regular file. (8) SEATING IS CONTAINED PER CORPUS: a `CorpusFileError` while the kernel seats a corpus (`seat_partition`) leaves nothing half-seated; `seat_store` marks THAT corpus failed (`store.failed_corpora`, with its code) and the server boots with the others; `lts_register_corpus` rolls back and answers a coded refusal, so a retry succeeds. "Rolls back" COVERS: the partition is out of the store, the kernel holds no `_parts`/`_states`/`_roots` entry for it and the partition is unbound, the reverse-index cache is reset, and a boot-failed corpus's `failed_corpora` entry is KEPT (it is dropped only after a successful seat), so the corpus stays listed as failed with its code and queries on it answer that code. It does NOT cover: a ledger, a query-log line or a log record written by the attempt, which stay. NOT covered: a corpus that failed at boot is not retried until a restart or `lts_register_corpus`.
- [ ] [TOOL-REASON-IS-A-FIXED-CODE] The TOP-LEVEL `reason` of a tool reply, and the `reason` of any refusal or fault block at any depth (a dict that says `success: false` or carries `error_class` or `live_detail`), is a FIXED CODE matching `[a-z0-9][a-z0-9_.-]{0,63}`, never message text, a path or `str(exc)`, WHATEVER `success` SAYS (every nested dict is walked at any depth). A NESTED INFORMATIONAL `reason` (`extent.corpora_skipped[].reason`, `did_you_mean_semantic.reason` when no corpus is named, a property-loss finding's `reason`) is either such a code OR a module-level CONSTANT sentence registered in `info_reasons()` (`factlattice_engine/reason_codes.py`): path-free by construction, never built from caller input, a path, a count, a hash or an exception message; a sentence not in the closed registry is a defect (`tests/test_reason_sites.py` is a TRIPWIRE for the literal, f-string, format-call and concatenation forms only, with per-site exemptions, and it CANNOT see a variable built elsewhere, a subscript assignment, a conditional expression, a subscript value or `setdefault`; the RUNTIME battery over real replies is the evidence, not the scan). A failed-heal block (`heal`) and a typed writer's nested `ledger` block are FAULT blocks: their `reason` is a code (`self-heal-raised`, `ledger-write-failed`, `undo-blob-not-stored`, `ledger-skipped-ephemeral`), a heal block's fixed sentence is `explanation` (one of the closed `HEAL_REASONS`; every `HEAL_REASONS` entry needs a `HEAL_REASON_CODES` entry, 1:1, pinned by a test) and an exception's text is `live_detail` (a ledger block has no `explanation`). Every route that prints a ledger failure for the operator prints the code AND the text, through `ledger.describe()`: `WRITTEN, BUT NOT LEDGERED (ledger-write-failed): <live_detail>`. The typed-writer exception below applies to the three typed writers only: a `success: true` reply that carries a `reason` (`lts_semantic_find` with `status: unavailable` says `weights-missing`) is held to it, and the sentence or path that used to ride in it goes in a separately named LIVE-ONLY field (`live_detail`, with a NEVER-persist note) that the query log never reads. A reply that also carries `error` must not begin that text with caller-supplied text. The one documented exception is the typed writers' `refused: true` reply, whose `reason` is a human sentence (pinned byte-for-byte) and whose fixed code is `evidence.refusal`; the query log therefore takes the code from `evidence.refusal` for a refused reply and from `reason` otherwise, and only when it matches the pattern. A reviewer helper (`python -m factlattice_engine.reviewer <verb>`, 14 verbs) holds the same rule on ANY failure, raised OR in-band: `reason` is a code from the closed list `HELPER_REASON_CODES` (`factlattice_engine/reviewer/__main__.py`); `error_class` is never null (the exception class, `ToolError` for an engine tool's text failure, `RegistryError` for a registry stop, `InBand` for a failure the helper itself reports: `lint-incomplete`, `self-gate-failed`, `registry-mismatch`, `registrations-not-projected`, `extension-is-the-reviewed-document`, `corpus-not-served`, `own-corpus-ambiguous`, and the `resolve-output` refusal codes of `RESOLVE_REFUSALS`); there is no `error` key; prose that explains a code is `explanation`, a FIXED sentence with nothing interpolated into it, so it is path-free by construction; the raw message is `raw_error`, and any structure that holds full paths is `terminal_only`, each beside a NEVER-persist note. A helper's `main` turns every Exception, every non-zero SystemExit and every other BaseException except KeyboardInterrupt into the contract (it does NOT cover KeyboardInterrupt, `--help`, an import-time failure, or a stdout that cannot be written at all, which the procedure's unparseable-reply stop covers): `usage-error` (exit 2) and `helper-crashed` (exit 3, distinct from the findings-only exit 1 of `gen6-scan`) are on the list, and the procedure treats an unparseable reply as the stop `helper-output-unreadable`. "No planted DIRECTORY name outside the terminal-only keys" is the claim; caller or registry text that is not a directory name IS echoed by design (`resolve-output` `folder` is the sanitised corpus id, `site_config` and `checks[].site_config` carry the site-config corpus id (`checks[].reason` is the code `default-root-used-without-overrides`), `registry-check` `registry_mcp` carries the MCP-supplied source, `evidence` echoes its `text`, `lint-groups` examples are document content). A path is kept out by STRUCTURE (a field a persisted record never copies), never by a pattern over free text. Pinned by a battery over every tool x argument shapes WITH and WITHOUT `text` that checks every reply carrying a `reason`, `success: true` included (`tests/test_tool_reason_codes.py`), and by `tests/test_reviewer_reasons.py`, which drives the failures of ALL 14 helper verbs for real in directories whose names hold spaces, both quote kinds and unicode, and FAILS when a verb of the parser is missing from its coverage list.

**Process**
- [ ] Each new test is shown FAILING on the pre-change commit; a test that passes before the fix is labelled a regression pin, not a RED.
- [ ] Commits go through a gate that reads pytest's EXIT STATUS, not its piped output: `tools/commit-if-green <worktree> -m ...`.
- [ ] A branch rebased onto a moved `main` whose new commits touch the same files is re-reviewed at the rebased tip (a clean range-diff proves identical patches, not identical composition).
- [ ] [PORTED-DEF-INVARIANTS] (c1, Part D review P2-1) A definition ported into `agents/` from another family joins `PORTED_DEFS` in `tests/test_ported_agent_defs.py` in the same change, so its invariants (tool list, denylisted names, boundary lines) are pinned from its first commit.
- [ ] [SHARED-STEP-COPIES] (c2, Part D review P2-1) A definition block copied into other defs (today the gap analyzer's Step 0) is pinned byte-identical across its copies by a test, so a change to one copy fails until every copy changes with it.
- [ ] [MARKER-SENTENCES] (c3, Part D review P2-1) A sentence a test pins as a marker is stated in the spec, and is changed only together with the test; a marker that exists only in a test is an unwritten requirement.
- [ ] [DSD-SELECTION-CITATION] (r21, AGENT-DEF-CHECKLIST, adopted 2026-10-07) An option the human SELECTED in a decision dialog is cited as a SELECTION (the option wording is the author's, named), never quoted as the human's own words; only text the human typed is his words.
- [ ] [PUBLISH-EXCLUDE-CLASSIFIED] A new top-level path, a new `agents/*.md`, or a new tool or document that names the deployment is classified in `PUBLISH-EXCLUDE` in the SAME change: public (a `# PUBLIC <name>` line), internal (an active entry with its reason) or pending (`#PENDING`, which is scanned until promoted). `tests/test_publish_exclude_classified.py` fails when an agent definition is unclassified. A publication snapshot is built mechanically from the list, so an unclassified file is a file nobody decided about.
- [ ] [PUBLISH-VOCABULARY-GROWS] A change that introduces a new deployment name, product, agent or role name, id family or machine path adds a row for it to the private publish vocabulary in the SAME change, case-insensitive, with a positive control (`tools/disclosure_guard.py` refuses a row that misses its own control at load, and `--tree` refuses to run without the vocabulary). The vocabulary is a closed list: it finds only what someone listed, so a snapshot is also scanned by an instrument that shares no list (capitalised and id-shaped tokens defined nowhere in the tree).

## 8. Stage 5: Deploy

| Principle | Rationale |
|-----------|-----------|
| Verify before, during, and after | "docker compose up succeeded" is not verification. Service responding to requests is verification. |
| Update documentation | An undocumented service is a forgotten service. |
| Never delete data without approval | Export before remove. |
| Report rollback instructions | Every deployment includes how to revert. |

## 9. Stage 6: Maintain

### 9.1 Spec Densification

Over time, specs accumulate narrative from conversational editing. Densification compresses without semantic loss.

| Tool | When | Purpose |
|------|------|---------|
| **factlattice-densifier** | Spec bloated from edits | Compresses prose to semantic essence |
| **factlattice-signal-loss-reviewer** | Always after densifier | Compares original vs densified. PASS / PASS_WITH_NOTES / FAIL. |

### 9.2 Corpus Health

| Tool | When | Purpose |
|------|------|---------|
| **factlattice-corpus-analyzer** | End of session, after major changes | Cross-corpus analysis: emergent concepts, missing references, definition drift, orphaned definitions, convergence candidates |

### 9.3 Spec-Implementation Drift

1. Run `factlattice-gap-analyzer` to identify drift
2. Determine whether spec or implementation is authoritative
3. Spec authoritative (default): fix implementation
4. Implementation discovered better design (confirmed by human): update the spec through the spec editor, then lint

### 9.4 Semantic Versioning

When specs change, author a DELTA document capturing the semantic meaning of the change using the `{change, context_for_change}` primitive. The DELTA is part of the check-in, not an afterthought. See SPEC.md Section 8 for the full DELTA document format and authoring model.

## 10. Trigger Map

### 10.1 Mandatory Triggers

| Trigger Event | Agent | Rationale |
|---------------|-------|-----------|
| .lts file written or edited | **factlattice-linter** | Format errors propagate to every consumer |
| Spec ready for build dispatch | **Architect review** | Design flaws caught here save a build-gap-fix cycle |
| Build complete | **First bringup** | Static analysis cannot find runtime bugs |
| Implementation exists, no independent tests | **QA tester** | Builder-written tests verify builder's model; independent tests verify spec |
| All quality dimensions pass | **Deployer** | Deployment includes verification and documentation |

### 10.2 Conditional Triggers (Architect-Decided)

| Trigger Condition | Agent | When to Skip |
|-------------------|-------|-------------|
| Touches auth/crypto/access control | **Security reviewer** | Pure UI or display-only components |
| Major refactor or critical path | **Code quality auditor** | Routine feature work |
| Integrates two systems | **Integration triangulator** | Single-system specs |
| MCP tool or bootstrap path | **Context economist** | Components outside context window |
| Spec grown through editing | **factlattice-densifier** → **signal-loss-reviewer** | Spec written once, not modified |
| Session ending, specs modified | **factlattice-corpus-analyzer** | No .lts files changed |

### 10.3 The Inner Loop vs The Outer Loop

```
INNER LOOP (per feature, runs many times per session):
  spec → lint → dispatch (with flags) → build + adjacent agents → bringup → gap-analyze → fix

OUTER LOOP (per session or per milestone):
  corpus-analyze → densify → signal-loss-review → DELTA authoring → handoff

INTEGRATION LOOP (per external system integration):
  profile external system → write integration spec → triangulate → fix → lint → inner loop

SCHEDULED (nightly, independent of build cycles):
  code quality sweep → quality event stream → findings accumulate for review
```

## 11. Quality Event Stream

Every agent MUST emit structured JSONL events to `{corpus}/events/quality.jsonl`. This is how the SDLC demonstrates measurable value.

See SPEC.md Section 11.2 for event schemas and the `QUALITY-EVENT-PROTOCOL.md` in the agents directory for implementation details.

Aggregatable metrics:

| Metric | What It Shows |
|--------|--------------|
| Findings by severity over time | Quality trend — P0s should decrease |
| First-pass resolution rate | Builder effectiveness — high rate = good spec clarity |
| Mean cycles to resolve | Process friction — lower = faster feedback loops |
| Agent effectiveness by type | Which quality dimensions catch the most issues |
| Densification token savings | Corpus maintenance ROI |

## 12. Anti-Patterns

| Anti-Pattern | Correct Approach |
|-------------|-----------------|
| Skip linting because "the spec looks fine" | Lint every spec. Cheapest gate in the lifecycle. |
| Run all quality dimensions at once | Run iteratively: dimension → fix → next dimension. |
| Builder decides to invoke security review | Architect decides. Builder orchestrates. |
| Add two-stage review to every build | Adjacent agents are normally false, callable on judgment. |
| Fix runtime bugs in the main conversation | Delegate to bringup agent. Save context for design. |
| Skip corpus analysis at session end | Run it. File-level improvements are invisible at corpus level. |
| Densify without signal-loss review | Always pair. Densifier compresses; reviewer verifies. |
| Code quality review inline on every cycle | Nightly scheduled sweep catches drift without blocking builds. |
