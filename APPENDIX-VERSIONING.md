# Appendix: Versioning, Change Tracking, and Impact Assessment

**Parent document**: the FactLattice Architecture Review Dossier (not published)
**Date**: 2026-03-29
**Status**: Draft — operational appendix for architect review

> **Design, not shipped in this repository.** The corpus-proposals MCP service (`corpus_proposals_*` tools) and the change-record generator described below are a design. They are not implemented here, and the `corpus_proposals_*` tools do not exist in this repository's engine. Read the proposal-service workflow as the context the change-record mechanism was designed for.

---

## The Problem

A single push to main may touch several parts of a corpus — a credential model, the step graph of a process flow, a glossary entry — affecting different audiences differently. Git tells you "47 lines across 3 files." That is a file-level diff. It tells you nothing about which concepts changed, whether those changes break downstream consumers, or who needs to care.

The semantic diff should say: "one breaking change to `[CRED-TOKEN]` (affects mobile devs), one additive flow step in `[FLOW-TOKEN-REQ]` (affects QA), one cosmetic glossary fix to `[TERM-LEDGER]` (affects no one)."

This appendix defines the mechanisms for producing that semantic diff from a FactLattice corpus — capturing changes, classifying their impact, computing blast radius through the graph, and filtering the result by audience.

---

## 1. Change Capture Mechanism

### 1.1 Current State

The corpus-proposals MCP service (a design; not shipped in this repository) manages the governance lifecycle of corpus changes: submit, review, approve/reject/defer, apply. This workflow handles the *intent* of a change but does not capture the *effect*. A proposal says "I want to add a flow step to `[FLOW-TOKEN-REQ]`." After approval and application, no structured record exists of what nodes, edges, and properties actually changed.

The existing versioning mechanisms in the base document format are document-scoped:
- **Frontmatter**: `version-scope`, `supersedes-version`, `breaking-changes` — major version lines only
- **Footer**: `**Version**`, `**Status**`, `**Last Updated**`, `**Changes**` — human-readable changelog
- **Graph index**: `content_hash` per node, `files_hash` per corpus — mechanical diff substrate, but no interpretation layer

These mechanisms tell you *that* something changed. They do not tell you *what kind of change it was* or *who it affects*.

### 1.2 Extended Workflow

The corpus-proposals workflow gains one new stage: after a change is applied, a change record is auto-generated by diffing the graph index before and after.

```
1. Friction identified → proposal submitted (corpus_proposals_submit)
2. Architect reviews → approved (corpus_proposals_approve)
3. Intelligence applies change → linter validates → committed
4. Change record auto-generated:
   a. Snapshot graph_index.json BEFORE and AFTER the commit
   b. Diff the two snapshots (Section 4)
   c. Classify each change by impact (Section 3)
   d. Derive affected audiences from frontmatter + edge analysis
   e. Write the change record as a FactLattice file
5. Change record published to JSONL event stream + MkDocs site
6. Stakeholders query changes filtered by role
```

The change record is generated by tooling, not authored by a human or Intelligence. It is a computed artifact derived from two graph index snapshots. The Intelligence that applied the change does not write the change record — it is produced mechanically to prevent editorial bias ("I only changed a small thing" when the graph diff shows a cascade).

### 1.3 Direct Commits (No Proposal)

Not every change goes through the proposal workflow. Direct commits by an Intelligence during a session (spec authoring, densification, build fixes) bypass the governance pipeline. These still generate change records if the tooling is configured to snapshot the graph index on every commit. The change record captures the same diff — it simply lacks the proposal ID linkage.

The recommendation: graph index snapshots are taken at every commit to `main` via a post-commit hook. The diff between consecutive snapshots produces a change record. Proposal-originated changes carry the proposal ID; direct commits carry the session ID from the engineering log.

## 2. Change Record Format

A change record is a FactLattice file. It uses the same notation, the same frontmatter schema, the same property format. It can be parsed into the graph index, traversed by lts-engine, and rendered by MkDocs. It is not a special format — it is a FactLattice document with a specific structure.

### 2.1 Document Structure

```markdown
---
scope: "Change record for commit abc1234 — 3 files, 2 nodes modified, 1 edge added"
audience: "Stakeholders of [CRED-TOKEN], [FLOW-TOKEN-REQ], [TERM-LEDGER]"
boundary: "Records what changed in this commit; does not explain why (see linked proposal)"
parent: changelog/2026-03.lts
depends-on: []
confidentiality: internal-only
---
# Change Record 2026-03-29-001 [DELTA:CR-2026-03-29-001]

> Breaking change to [CRED-TOKEN] signing flow; additive step in [FLOW-TOKEN-REQ]; cosmetic fix to [TERM-LEDGER].

## Scenario Changes

Scenario changes are tracked separately from general node changes because they encode the acceptance contract, route automatically to verification roles, and follow a finer-grained impact-classification table (Section 3.2). The auto-generator detects Scenario nodes via the `node_kind: scenario` marker emitted by the parser (SPEC.md §5.5.5).

### [SCEN-TOKEN-V2-PARSE-REJECTS-V1] v2 parser rejects v1 payload (parent: [CRED-TOKEN])

- change-type: added
- impact: additive
- affected-roles: qa-engineer, test-author, mobile-dev
- scenario-content:
  - when: a v1-formatted scope policy blob is submitted to the v2 parser
  - then: the parser returns 400 with detail indicating "scope policy version unsupported"
- rationale: Acceptance criterion paired with the breaking [CRED-TOKEN] format change; provides verifiable test wiring for downstream consumers

### [SCEN-TOKEN-V1-PARSE-LEGACY] v1 parser path preserved for legacy clients (parent: [CRED-TOKEN])

- change-type: removed
- impact: breaking
- affected-roles: qa-engineer, test-author, mobile-dev, integration-tester
- prior-scenario-content:
  - when: a v1-formatted scope policy blob is submitted to the legacy v1 parser
  - then: the parser accepts the blob and emits the structured token
- rationale: v1 parser path is being removed alongside the v2 cutover; downstream tests that exercised this path must be retired or re-pointed at v2
```

### 2.2 Impact Classification Vocabulary

Every node change and edge change carries an `impact` property from this hierarchy (ordered from most to least severe):

| Impact | Meaning | Consumer Action |
|--------|---------|-----------------|
| **breaking** | Existing consumers of this node will malfunction without updates. Structural change to properties, removal of expected content, incompatible redefinition. | Must update consuming code/specs/tests |
| **additive** | New content that does not alter existing behavior. New flow steps, new properties, new edges. Consumers that ignore the new content continue working. | Should update tests to cover new content |
| **deprecation** | Existing content marked for future removal. Still functional but consumers should migrate. | Should plan migration before removal |
| **cosmetic** | Rewording, reformatting, density improvement with confirmed semantic equivalence. No behavioral change. | No action required |
| **correction** | Fix to an error in the prior version. The prior version was wrong; this version is right. Consumers relying on the prior (incorrect) behavior may need updates. | Should verify not depending on the corrected (wrong) behavior |

The distinction between **breaking** and **correction** matters. A breaking change alters correct behavior. A correction fixes incorrect behavior. Both may require consumer updates, but corrections carry lower organizational urgency — the prior state was a bug, not a contract.

### 2.3 Document Type Tag and Prefix

Change records use document type tag `DELTA` and node prefix `CR-` (Change Record):

- `[DELTA:CR-2026-03-29-001]` — document-level identifier
- `CR-` prefix registered in whatever domain profile governs the corpus

The `DELTA` tag is a candidate for core promotion (used by every domain that tracks changes). The `CR-` prefix is a convention that domains may override.

## 3. Impact Assessment Model

### 3.1 Role-Based Filtering

Not every change matters to every person. A mobile developer does not need to know about an architecture refactoring that does not change any API surface. A QA engineer does not need to know about a cosmetic glossary fix.

Role-based filtering uses two inputs:

1. **Document `audience` frontmatter**: Every FactLattice file declares its audience. A change to a document with `audience: "Mobile SDK developers"` is relevant to mobile developers.
2. **Edge analysis**: A change to `[CRED-TOKEN]` is relevant to anyone whose work DEPENDS_ON or IMPLEMENTS that node, even if they never read the CRED-TOKEN document directly. The graph tells you who is downstream.

The change record's "Impact by Audience" table is computed, not authored. The process:

1. For each changed node, read the `audience` frontmatter of its source document.
2. Parse audience strings into role tokens (mobile-dev, backend-dev, qa-engineer, security-reviewer, architect, etc.). A vocabulary of role tokens should be defined per domain profile.
3. Walk reverse DEPENDS_ON and IMPLEMENTS edges from the changed node. For each reachable node, add that node's audience roles to the affected set.
4. For each role, filter to show only the changes they are affected by, and report the highest impact level among those changes.

### 3.2 Impact Classification Assignment

Impact classification is assigned per node change by comparing the before and after snapshots:

| Signal | Classification |
|--------|---------------|
| Node removed entirely | breaking |
| Node added (new) | additive |
| Required property removed or type-changed | breaking |
| Required property value changed (semantic change) | breaking or correction (requires context) |
| New property added | additive |
| Property value reworded, semantic equivalence confirmed | cosmetic |
| Node status changed to `deprecated` | deprecation |
| Content hash changed but diff shows only whitespace/formatting | cosmetic |
| Content hash changed with substantive diff | Analyze per property (may be mixed) |
| **Scenario added on existing parent node** (new acceptance criterion under an existing requirement / capability / flow) | **additive** |
| **Scenario removed without replacement** (acceptance criterion retired) | **breaking** — the contract surface shrank; downstream tests that depended on this Scenario lose their normative anchor |
| **Scenario removed and replaced by one with equivalent coverage** | **correction** — flag for human review of the equivalence claim |
| **Scenario `when` clause modified** (different triggering condition) | **breaking** — the contract surface shifted; consumers wiring tests to this Scenario need to update |
| **Scenario `then` clause modified** (different expected outcome) | **breaking or correction** — breaking if the prior expectation was correct contract; correction if it was a mis-statement |
| **Scenario `and-when` / `and-then` conjunct added** | **breaking** — tightens the criterion; existing test wiring may need additional assertions |
| **Scenario `and-when` / `and-then` conjunct removed** | **additive** — loosens the criterion; existing test wiring continues to pass |
| **Scenario `given` precondition added or modified** | **additive** if it narrows applicability without changing the contract for the main case; **breaking** if it removes the Scenario's coverage of a case the prior version covered |
| **Scenario title reworded with semantic equivalence confirmed** | **cosmetic** |

Distinguishing **breaking** from **correction** requires context that the mechanical diff cannot provide. The change record marks these as `breaking (review: may be correction)` and flags them for human or Intelligence review. If the change originated from a proposal, the proposal's rationale field provides this context.

### 3.3 Blast Radius via lts-engine Causal Traversal

The blast radius of a change is the set of nodes transitively affected. This is computed using the impact analysis algorithm already defined in the lts-engine traversal engine specification (Dossier Section 1.1, Layer 3):

```
blast_radius(changed_node) =
  incoming: reverse traversal of DEPENDS_ON + IMPLEMENTS edges
    → "who depends on this node?"
  outgoing: forward traversal of CASCADES_TO + ENABLES + PRECONDITION_FOR edges
    → "what does this node cascade to?"
  depth: configurable, default 3
  budget: configurable, default 50 nodes
```

The blast radius is included in the change record as a flat list of reachable nodes with the edge path that connects them. This lets a reader see not just "these nodes are affected" but "this is *why* they are affected" — the chain of dependencies.

For a breaking change to `[CRED-TOKEN]`:
- Reverse DEPENDS_ON finds `[FLOW-TOKEN-REQ]`, `[FLOW-REVOKE]`, `[SVC-VAULT]`, `[TEST-TOKEN-ISSUING]`
- Forward CASCADES_TO finds `[CRED-TOKEN-ISSUER-AUD]` (revocation cascade)
- These nodes collectively span audiences: mobile-dev, backend-dev, security-reviewer, qa-engineer, integration-tester

The blast radius computation reuses the existing lts-engine traversal engine. No new algorithm is needed — the impact analysis traversal policy is already specified. The change record tooling invokes lts-engine with the changed nodes as entry points and the impact analysis policy.

### 3.4 Audience Derivation

Audience derivation combines four signals:

1. **Direct audience** (from `audience` frontmatter of the changed node's document)
2. **Transitive audience** (from `audience` frontmatter of documents containing nodes in the blast radius)
3. **Role registry** (from the domain profile's role vocabulary, mapping audience strings to canonical role tokens)
4. **Node-kind audience** — when a changed node carries `node_kind: scenario`, the change automatically routes to verification roles (qa-engineer, test-author, integration-tester) in addition to the parent node's audience. Scenarios are acceptance contracts; verification roles are always in scope for Scenario changes. Domain profiles MAY extend node-kind-based routing via `change_tracking.node_kind_routing` in their profile YAML.

The domain profile should declare a role vocabulary:

```yaml
roles:
  mobile-dev: { aliases: ["Mobile SDK developers", "mobile developers", "iOS/Android"] }
  backend-dev: { aliases: ["Backend developers", "server-side", "API consumers"] }
  qa-engineer: { aliases: ["QA", "quality assurance", "testers"] }
  security-reviewer: { aliases: ["Security team", "security reviewers", "infosec"] }
  architect: { aliases: ["System architects", "architects", "Lead developer"] }
```

This mapping normalizes the free-text `audience` strings in existing documents to machine-comparable role tokens. Without it, "Mobile SDK developers" and "mobile devs" are different audiences. With it, they resolve to the same role.

## 4. Version Comparison (Graph Index Diffing)

### 4.1 The Diffing Substrate

The `graph_index.json` already contains everything needed for mechanical comparison:
- Per-node `content_hash` (SHA-256 of node content)
- Per-file content hashes in `source_corpus`
- Corpus-level `files_hash`
- Edge sets per layer with source, target, type, layer

Two snapshots of `graph_index.json` — one before a change, one after — contain sufficient information to compute the full semantic diff without reading any `.lts` files. The `.lts` files are consulted only for property-level diffing (what specifically changed within a modified node).

### 4.2 Snapshot Versioning

The `graph_index.json` must carry a monotonic version or content hash so two snapshots can be diffed mechanically and ordered unambiguously.

Current metadata in graph_index.json:
```json
{
  "version": "1.0",
  "generated_at": "2026-03-29T14:00:00Z",
  "source_corpus": {
    "root_path": "/path/to/corpus",
    "files_hash": "sha256:...",
    "file_hashes": { "file.lts": "sha256:..." }
  }
}
```

Required additions:
```json
{
  "snapshot_version": 47,
  "snapshot_hash": "sha256:...",
  "parent_snapshot_version": 46,
  "parent_snapshot_hash": "sha256:...",
  "commit_ref": "abc1234def5678"
}
```

| Field | Purpose |
|-------|---------|
| `snapshot_version` | Monotonically increasing integer. Enables ordering. |
| `snapshot_hash` | SHA-256 of the entire graph_index.json content (excluding this field itself). Enables integrity verification. |
| `parent_snapshot_version` | The snapshot this one was derived from. Enables chain-of-custody. |
| `parent_snapshot_hash` | Hash of the parent snapshot. Enables tamper detection. |
| `commit_ref` | Git commit hash that triggered this snapshot. Enables git correlation. |

This creates a chain of snapshots. Any two snapshots in the chain can be diffed. The chain is append-only — snapshots are never modified after creation.

### 4.3 Diff Algorithm

Given two graph index snapshots (before, after):

**Step 1: Node diff**
```
For each node_id in (before.nodes UNION after.nodes):
  if node_id in before but not after → REMOVED
  if node_id in after but not before → ADDED
  if before.nodes[node_id].content_hash == after.nodes[node_id].content_hash → UNCHANGED
  if before.nodes[node_id].content_hash != after.nodes[node_id].content_hash → MODIFIED
```

**Step 2: Edge diff (per layer)**
```
For each layer in [semantic, temporal, causal, entity]:
  before_edges = set of (source, target, type) tuples from before.layers[layer].edges
  after_edges = set of (source, target, type) tuples from after.layers[layer].edges
  added = after_edges - before_edges
  removed = before_edges - after_edges
```

**Step 3: Property diff (for MODIFIED nodes only)**

Read the `.lts` source files for modified nodes using the `line_range` from the graph index. Compare property-by-property:
```
For each property_key in (before_props UNION after_props):
  if key in before but not after → property REMOVED
  if key in after but not before → property ADDED
  if before_props[key] != after_props[key] → property CHANGED (include old and new values)
```

**Step 3a: Scenario diff (for nodes where node_kind == scenario)**

Scenarios are tracked as a structured behavioral contract, not just a property bag. When a node carries `node_kind: scenario` in either snapshot, the diff additionally emits a `scenario_diff` record:

```
For a Scenario node in (before UNION after):
  if before lacks the node, after has it     → scenario ADDED       (impact: additive)
  if before has the node, after lacks it     → scenario REMOVED     (impact: breaking by default; correction if replacement Scenario covers same case)
  if before.when != after.when               → scenario WHEN_MODIFIED   (impact: breaking)
  if before.then != after.then               → scenario THEN_MODIFIED   (impact: breaking-or-correction; flag for review)
  if before.and_when_set != after.and_when_set → scenario CONJUNCT_CHANGED  (impact: additive if removed, breaking if added)
  if before.and_then_set != after.and_then_set → scenario CONJUNCT_CHANGED  (impact: additive if removed, breaking if added)
  if before.given != after.given             → scenario GIVEN_CHANGED   (classification per Section 3.2)
  if before.title != after.title && content unchanged → scenario REWORDED (impact: cosmetic)
```

The Scenario diff is emitted in the change record under a dedicated `## Scenario Changes` section (Section 2.1), distinct from the general `## Node Changes` section. This separation lets downstream consumers (test-coverage analyzers, BDD-test-generators) filter Scenario diffs without parsing the full node diff.

**Audience auto-routing**: Scenario diffs auto-route to verification roles (qa-engineer, test-author, integration-tester) per Section 3.4 signal 4, in addition to whatever audience the Scenario's parent node carries.

**Step 4: Impact classification (per change)**

Apply the classification rules from Section 3.2 to each node change and edge change.

**Step 5: Blast radius computation**

For each MODIFIED, ADDED, or REMOVED node with impact >= additive, run the lts-engine impact analysis traversal from that node.

**Step 6: Audience derivation**

For each affected node (direct changes + blast radius), collect audience roles per Section 3.4.

**Step 7: Emit change record**

Assemble the change record document per Section 2.1.

### 4.4 Filtering and Presentation

The raw change record contains everything. Consumers filter it:

| Consumer | Filter | Sees |
|----------|--------|------|
| Mobile developer | `role: mobile-dev` | Only changes where mobile-dev appears in affected-roles |
| QA engineer | `role: qa-engineer` | Only changes where qa-engineer appears in affected-roles |
| Architect | `impact >= additive` | All non-cosmetic changes regardless of role |
| Release manager | `impact == breaking` | Only breaking changes |
| MkDocs site | All changes | Full change record rendered as a page |
| JSONL event stream | All changes | Each change emitted as a structured event |

A push touching 3 files becomes a structured change report with per-audience views. The mobile developer sees one breaking change they need to act on. The QA engineer sees one additive step they need to test. The architect sees the full picture. Nobody sees the cosmetic glossary fix unless they ask for it.

## 5. Integration with Existing Systems

### 5.1 Corpus-Proposals MCP

The corpus-proposals service manages governance: submit, review, approve, apply. Change records extend this lifecycle with a post-apply step.

```
corpus_proposals_submit → PROP-047 created (pending/)
corpus_proposals_approve → PROP-047 moved to approved/
Intelligence applies change → commit abc1234
Post-commit hook:
  1. Rebuild graph_index.json (new snapshot)
  2. Diff against previous snapshot
  3. Generate change record [DELTA:CR-2026-03-29-001]
  4. Link change record to PROP-047
  5. Emit JSONL event
```

The change record carries a `proposal` field linking back to the originating proposal. The proposal carries a `change-record` field linking forward to the generated record. Bidirectional traceability: why was this change made (proposal rationale) and what did this change actually do (change record diff).

A new MCP tool — `corpus_proposals_get_change_record` — returns the change record for an approved proposal, enabling stakeholders to query the actual effect of a governance decision.

### 5.2 SDLC Integration

The SDLC lifecycle (spec -> lint -> review -> build -> test -> deploy) gains change records at two integration points:

**Session handoff**: Change records generated during a session are included in the handoff artifacts. The next session's Intelligence reads them to understand what changed since the last session without re-reading every modified file. The change record is a compressed representation of "what happened" — denser than a git log, more structured than a prose summary.

**Gap analyzer input**: The spec-gap-analyzer currently compares a spec against its implementation. With change records, it can also compare the *current* spec against the *previous* spec and flag gaps between the spec's evolution and the implementation's evolution. If the spec gained a new flow step but the implementation did not gain the corresponding code path, that is a drift signal.

**Release quality gate**: The release-quality-gate agent (SDLC Section 9.3) currently runs all quality dimensions. With change records, it can scope its analysis: only run security review on changes classified as `breaking` that touch security-prefixed nodes (CRED-*, SC-*, CW-*). Only run spec-gap analysis on changes classified as `additive` or `breaking`. Skip cosmetic changes entirely. This reduces quality gate cost proportional to change scope.

### 5.3 JSONL Event Streams

Change events are a natural fit for the JSONL event stream pattern defined in Dossier Section 8. A change record generates a JSONL event:

```json
{
  "type": "corpus_change",
  "id": "CR-2026-03-29-001",
  "date": "2026-03-29T14:30:00Z",
  "source": "post-commit-hook",
  "commit": "abc1234def5678",
  "proposal": "PROP-047",
  "session": "session-2026-03-29a",
  "highest_impact": "breaking",
  "nodes_modified": ["CRED-TOKEN", "FLOW-TOKEN-REQ", "TERM-LEDGER"],
  "nodes_added": [],
  "nodes_removed": [],
  "edges_added": [{"source": "FLOW-TOKEN-REQ", "target": "CRED-TOKEN", "type": "DEPENDS_ON"}],
  "edges_removed": [],
  "affected_roles": ["mobile-dev", "backend-dev", "security-reviewer", "qa-engineer", "integration-tester"],
  "change_record_path": "changelog/CR-2026-03-29-001.lts"
}
```

This event is appended to the engineering log JSONL stream alongside session, discovery, task_completed, and decision entries. It enables temporal queries: "what changed in this corpus during March 2026?" is answered by filtering the JSONL stream for `type: corpus_change`.

The JSONL event is a summary. The full change record (with property diffs, blast radius, and per-audience tables) lives in the FactLattice file. The JSONL event points to it.

### 5.4 Git Correlation

Git diff is file-level. FactLattice diff is concept-level. Both are useful. They are not redundant.

| Dimension | Git Diff | FactLattice Diff |
|-----------|----------|--------------|
| Granularity | Lines in files | Nodes, edges, properties in graph |
| Impact classification | None | breaking / additive / deprecation / cosmetic / correction |
| Audience filtering | None | Per-role views |
| Blast radius | None | Transitive via DEPENDS_ON / CASCADES_TO |
| Cross-file awareness | File-by-file | Graph-wide (change in file A may affect node in file B via edges) |
| Machine readability | Patch format | Structured FactLattice document + JSONL event |

The FactLattice diff is computed FROM the graph index snapshots, not from git. Git provides the trigger (post-commit hook) and the correlation key (commit hash). The graph index provides the semantic content.

A practitioner workflow: review the FactLattice diff first (what concepts changed and who is affected), then dive into the git diff only for the specific nodes that need attention (what exactly changed in the text).

## 6. End-to-End Process

From friction identified to stakeholders seeing what changed:

### Step 1: Friction Identified

A developer, Intelligence, or automated analysis identifies a problem — a gap in a spec, an incorrect definition, a missing flow step, a stale edge. The friction may surface during a build (spec-gap-analyzer finding), a session (practitioner observation), or a quality gate (security reviewer finding).

### Step 2: Proposal Submitted

The developer or Intelligence submits a corpus proposal via the MCP service (`corpus_proposals_submit`). The proposal describes what should change and why. It references the affected nodes by bracketed ID.

### Step 3: Architect Reviews and Approves

The architect reviews pending proposals (`corpus_proposals_list_pending`, `corpus_proposals_get`). Reviews the proposed change against the corpus architecture. Approves (`corpus_proposals_approve`), rejects with rationale, defers, or requests changes.

### Step 4: Intelligence Applies Change

An Intelligence applies the approved change to the corpus files. The factlattice-linter validates structural correctness. The change is committed to the repository.

### Step 5: Change Record Auto-Generated

The post-commit hook invokes `factlattice-delta-gen` (Section 8), which:
1. Loads the previous graph index snapshot from `.factlattice/cache/`
2. Builds a new graph index from the updated corpus
3. Runs the diff algorithm (Section 4.3): node diff, edge diff, property diff
4. Classifies each change by impact (Section 3.2)
5. Computes blast radius via lts-engine impact analysis traversal
6. Derives audience roles from frontmatter + edge analysis
7. Writes the DELTA document to `deltas/CR-{date}-{seq}.lts`
8. Emits `corpus_change` event to the JSONL engineering log stream
9. Caches the new snapshot for future diffs

### Step 6: Publication

The DELTA document lives in the repo at `deltas/` (queryable by Intelligences, accumulates history). It is also surfaced via:
- **MkDocs site**: "Recent Changes" section renders DELTAs as pages with linked bracketed IDs and per-audience filtering
- **JSONL event stream**: Summary event for temporal queries and dashboards
- **Notification system** (if configured): Role-filtered alerts ("mobile-dev: breaking change to [CRED-TOKEN]")

### Step 7: Stakeholder Query

Stakeholders query changes through their preferred interface:
- **MkDocs site**: Browse changelog, filter by role, click through to affected nodes
- **lts-engine traversal**: Start from a node, traverse to its change history via computed edges from JSONL events
- **JSONL queries**: Filter event stream by role, impact level, date range, or node
- **MCP tool**: `corpus_proposals_get_change_record` returns the structured change record for a specific proposal

## 7. Format Implications

### 7.1 Frontmatter Versioning — What Exists Is Sufficient

The existing frontmatter keys (`version-scope`, `supersedes-version`, `breaking-changes`) handle major version lines. Change records handle per-commit granularity. There is no need for a more complex frontmatter versioning scheme. The two mechanisms operate at different scales:

| Scale | Mechanism | Example |
|-------|-----------|---------|
| Major version (1.x -> 2.x) | Frontmatter `version-scope` + `supersedes-version` | PostgreSQL migration, API v2 |
| Per-commit | Change record [DELTA:CR-*] | Added flow step, fixed definition |

Adding a `last-change-record` frontmatter key to documents is tempting but creates a maintenance burden — every commit touching a document must update its frontmatter. The graph index already links documents to their change history via content hashes. Let the tooling compute the link; do not force authors to maintain it.

### 7.2 New Document Type Tag: DELTA

Change records use document type tag `DELTA`. This is a new tag to be added to the core type tag registry (SPEC Section 3.1).

| Type Tag | Purpose | Typical Content | Example |
|----------|---------|----------------|---------|
| DELTA | Change record (auto-generated) | Node diffs, edge diffs, impact classification, blast radius, audience table | `[DELTA:CR-2026-03-29-001]` |

DELTA is a core tag, not a domain tag. Every domain that tracks changes uses the same change record structure. The content of the change record (which nodes, which properties) is domain-specific. The structure is universal.

### 7.3 New Node Prefix: CR-

Change record nodes use prefix `CR-` (Change Record). This prefix should be registered as core because change tracking is a cross-domain concern.

| Prefix | Category | Typical Parent Doc Type | Example |
|--------|----------|------------------------|---------|
| CR | Change record | DELTA | `[CR-2026-03-29-001]` |

### 7.4 No New Section Type Needed

A `## Change Log` section within regular FactLattice documents was considered and rejected. Change history belongs in separate DELTA documents, not embedded in the documents they describe. Reasons:

1. **Unbounded growth**: A change log section in a long-lived document grows without limit. The document becomes a historical record instead of a specification.
2. **Cross-cutting changes**: A single commit may touch nodes in multiple documents. The change record is per-commit, not per-document.
3. **Separation of concerns**: The specification says what IS. The change record says what CHANGED. These are different documents for different audiences.

The existing footer `**Changes**` field remains appropriate for human-readable annotation of the most recent significant change. It is a convenience for readers, not a structured change tracking mechanism.

### 7.5 Graph Index Snapshot Versioning

The `graph_index.json` format requires the additions specified in Section 4.2:

```json
{
  "snapshot_version": 47,
  "snapshot_hash": "sha256:...",
  "parent_snapshot_version": 46,
  "parent_snapshot_hash": "sha256:...",
  "commit_ref": "abc1234def5678"
}
```

These fields are added to the build metadata section of the graph index. They do not affect the node or edge schemas. The parser does not need modification — these are metadata fields consumed by the diff tooling, not by the traversal engine.

Snapshot storage: graph index snapshots can be stored as compressed JSON in a `snapshots/` directory alongside the graph index, or in a dedicated snapshot store. The storage mechanism is an implementation concern. The format concern is that the snapshot carries enough metadata to be diffed against any other snapshot in the chain.

### 7.6 Domain Profile Extension

Domain profiles (Dossier Section 2.1) should declare their role vocabulary for audience derivation:

```yaml
# In domain-profile.yaml, new section:
change_tracking:
  role_vocabulary:
    mobile-dev: { aliases: ["Mobile SDK developers", "mobile developers"] }
    backend-dev: { aliases: ["Backend developers", "server-side"] }
    qa-engineer: { aliases: ["QA", "quality assurance", "testers"] }
    security-reviewer: { aliases: ["Security team", "infosec"] }

  event_stream:
    entry_type: "corpus_change"
    file_pattern: "logs/engineering/{YYYY-MM}.jsonl"
    references: [nodes_modified, nodes_added, nodes_removed, proposal, session]

  snapshot_storage:
    path: "snapshots/"
    retention: "all"  # or "last-N" for bounded storage

  node_kind_routing:                  # optional; extends audience derivation per node_kind
    scenario:
      auto_route_to: [qa-engineer, test-author, integration-tester]
      # Scenarios always reach verification roles, regardless of parent's audience
```

This is a natural extension of the domain profile model. The role vocabulary is domain-specific (a Medical domain has roles like clinician, nurse, patient-advocate that an Enterprise domain does not). The event stream declaration follows the pattern established in Dossier Section 4.4.

## 8. Automated Hook Mechanism — Push-to-DELTA Pipeline

### 8.1 Concept

Every push to `main` on any FactLattice corpus — regardless of git host — triggers a pipeline that:

1. Diffs the graph index (before vs. after)
2. Generates a DELTA document with impact assessment
3. Publishes the change record
4. Opens the summary for human review

The trigger is platform-specific. The work is platform-agnostic. One tool (`factlattice-delta-gen`) does the semantic diffing; the hooks just call it.

### 8.2 Architecture

```
Push to main
    │
    ├── CI/CD server ──→ webhook to build-host:9000
    ├── GitHub ─────────→ webhook to receiver (or GitHub Action)
    ├── Local git ──────→ post-merge hook on developer machine
    │
    └── All invoke: factlattice-delta-gen
            │
            ├── 1. Load previous graph_index.json (cached snapshot)
            ├── 2. Parse current HEAD .lts files → new graph index
            ├── 3. Diff: node hashes, edge sets, property values
            ├── 4. Classify impact per change (breaking/additive/cosmetic/...)
            ├── 5. Compute blast radius via lts-engine traversal
            ├── 6. Derive affected audiences from frontmatter + edges
            ├── 7. Emit DELTA document (FactLattice file)
            ├── 8. Append summary to change log
            ├── 9. Log corpus_change event to JSONL stream
            └── 10. Notify (open doc / publish to MkDocs / post to channel)
```

### 8.3 The `factlattice-delta-gen` Tool

A single CLI tool that all hooks invoke:

```
factlattice-delta-gen
    --corpus <path>              # Corpus root (contains .lts files)
    --previous-index <path>      # Cached graph_index.json from last run
    --output-dir <path>          # Where to write DELTA document
    --commit-ref <sha>           # Git commit that triggered this
    --commit-message <string>    # For context in the change record
    --append-to <path>           # Append summary to this file (optional)
    --open                       # Open the summary file after generation (macOS `open`)
    --publish-to <url>           # POST change record to MkDocs webhook (optional)
    --jsonl-log <path>           # Append corpus_change event (optional)
```

The tool:
- Is written in Python (shares the FactLattice parser with MkDocs plugin and lts-engine)
- Caches the current graph index as `previous-index` for the next run
- Produces a `DELTA-{timestamp}.lts` file in the output directory
- Is domain-agnostic — reads domain profiles for role vocabulary and impact rules

### 8.4 Hook Implementations

**CI/CD server (example corpus)**

A webhook receiver at `:9000` triggers `poll-and-build.sh` on push. Extend it:

```bash
# In poll-and-build.sh, after git pull:
PREV_INDEX="/repo/cache/graph_index.json"
factlattice-delta-gen \
    --corpus "$REPO_DIR" \
    --previous-index "$PREV_INDEX" \
    --output-dir "$REPO_DIR/deltas/" \
    --commit-ref "$(git -C $REPO_DIR rev-parse HEAD)" \
    --commit-message "$(git -C $REPO_DIR log -1 --format=%s)" \
    --jsonl-log "$REPO_DIR/logs/changes.jsonl" \
    --publish-to "http://localhost:80/api/reload"
# Then proceed with mkdocs build as before
```

The DELTA documents become pages on the MkDocs site — a "Recent Changes" section in the nav.

**Local git (developer machine — any corpus)**

A post-merge hook (fires after `git pull` completes):

```bash
#!/bin/bash
# .git/hooks/post-merge
CORPUS_ROOT="$(git rev-parse --show-toplevel)"
CACHE_DIR="$CORPUS_ROOT/.factlattice/cache"
mkdir -p "$CACHE_DIR"

factlattice-delta-gen \
    --corpus "$CORPUS_ROOT" \
    --previous-index "$CACHE_DIR/graph_index.json" \
    --output-dir "$CORPUS_ROOT/deltas/" \
    --commit-ref "$(git rev-parse HEAD)" \
    --commit-message "$(git log -1 --format=%s)" \
    --append-to "$CORPUS_ROOT/CHANGELOG.md" \
    --open
```

The `--open` flag calls `open CHANGELOG.md` on macOS — the file opens in the default Markdown viewer (Marked, VS Code, or whatever's mapped) with the latest change summary appended at the top.

**GitHub (if used for any corpus)**

A GitHub Action:

```yaml
on:
  push:
    branches: [main]
    paths: ['**.lts']

jobs:
  delta:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 2  # Need previous commit for diff
      - run: pip install factlattice-tools
      - run: |
          factlattice-delta-gen \
            --corpus . \
            --previous-index .factlattice/cache/graph_index.json \
            --output-dir deltas/ \
            --commit-ref ${{ github.sha }} \
            --commit-message "${{ github.event.head_commit.message }}"
      - uses: actions/upload-artifact@v4
        with:
          name: delta-${{ github.sha }}
          path: deltas/
```

### 8.5 What the Developer Sees

**On push (developer machine)**:

A developer pushes changes to three corpus files. The post-merge hook fires (or a push wrapper triggers it). Five seconds later, a Markdown file opens showing:

```markdown
**Files changed**: 3 (.lts)

### Breaking (1)

  mutual TLS. Affects: mobile developers, integration testers.

- **[SYS-SIGNING-TRANSPORT]** New property: `mtls_required: true`
- **[TERM-SIGNING-CHANNEL]** New node added to glossary

### Cosmetic (4)

- 3 property reformattings (whitespace only)
```

**On the MkDocs site**:

A "Recent Changes" nav section shows the last N DELTA documents, each rendered as a page with linked bracketed IDs, per-audience filtering, and blast-radius diagrams derived from the graph at render time (SPEC.md §15) — never stored in the DELTA itself.

**In the JSONL stream**:

```json

 "commit": "abc1234", "source": "post-merge-hook",

```

### 8.6 Where DELTAs Live — In the Repo, Loop-Protected

DELTA files live in the repo at `deltas/DELTA-{date}-{short-sha}.lts`. They must be in the repo because:

- **Intelligences need to query them.** "What changed since I last looked?" requires reading DELTA files in the working directory. An Intelligence can grep DELTAs for specific nodes, filter by audience, summarize trends over months.
- **They accumulate history.** "Describe the major changes over the last 6 months" is answered by reading 6 months of DELTA files — this is only possible if they persist in the repo.
- **They're FactLattice files.** Bracketed IDs, impact classifications, audience tags — all queryable with the same tools that query specs.

**Circularity prevention**: The hook checks whether any non-delta FactLattice files changed. If the only changes are in `deltas/`, the hook is a no-op:

```
Push to main
  → hook fires
  → check: did any .lts files OUTSIDE deltas/ change?
  → YES: build graph index → diff → generate DELTA → commit to deltas/ → push
    → hook fires again → only deltas/ changed → NO-OP. Loop terminated.
  → NO: skip. Done.
```

Implementation in the hook:

```bash
# Check if any non-delta FactLattice files changed in this push
CHANGED=$(git diff --name-only HEAD~1..HEAD -- '*.lts' ':!deltas/')
if [ -z "$CHANGED" ]; then
    echo "Only delta files changed. Skipping."
    exit 0
fi
```

**What lives where**:

| Artifact | Where | Why |
|----------|-------|-----|
| DELTA `.lts` files | `deltas/` in repo | Queryable by Intelligences, accumulates history |
| `corpus_change` JSONL entry | Server-side log (also in repo JSONL if desired) | Dashboard/timeline rendering |
| Graph index snapshots | `.factlattice/cache/` (gitignored) | Local diff cache, per-machine |
| "Recent Changes" MkDocs page | Generated at build time from DELTAs | Human browsing |

**Intelligence queries enabled by persisted DELTAs**:

| Query | How |
|-------|-----|
| "What changed since last Tuesday?" | Read DELTAs with dates after Tuesday |
| "Did anything break the token issuing flow?" | Grep DELTAs for `[FLOW-TOKEN-SIGN]` + `impact: breaking` |
| "What should I care about as a mobile developer?" | Filter DELTAs by `audience: mobile` |
| "Summarize corpus changes over the last 6 months" | Read all DELTAs, aggregate by impact level and domain area |
| "What's different from when Sam last pulled?" | Compare Sam's cached snapshot against current HEAD |

### 8.7 Snapshot Management

The graph index cache is the lynchpin. If the previous snapshot is missing or corrupt, the tool can't diff — it falls back to generating a "full inventory" DELTA (everything in the current index treated as "added"). This is correct for first run but noisy for steady state.

**Cache strategy**:
- On each run, `factlattice-delta-gen` saves the current graph index to `--previous-index` path (overwriting)
- The cached index is gitignored (`.factlattice/cache/` in `.gitignore`)
- On the build server, the cache lives in the Docker volume (persists across container rebuilds)
- On a developer machine, the cache lives in the corpus `.factlattice/cache/` directory

**Multi-developer scenario** (a team): Each developer's machine has its own cache (their last-seen state). When Sam pulls and the hook fires, the diff is relative to Sam's last pull — not the other developer's last push. This is correct: Sam sees what changed *since Sam last looked*, not since the last commit. Different developers get different diffs based on their own cadence.

The existing infrastructure provides the substrate. The new mechanisms layer semantic interpretation on top of mechanical diffing. Git tells you what lines changed. The FactLattice diff tells you what concepts changed, how important those changes are, and who needs to know.
